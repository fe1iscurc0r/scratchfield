## 2. 新发现的耦合类：preload 读写**页面全局**

这是交接文档 §4.1 的阻塞清单里**没有**的一类，且危险在于**它不报错**——
隔离后 preload 里的 `window.showStatusToast = fn` 写的是 preload 自己的世界，
页面侧调用照旧是 `undefined`/旧实现，功能静默降级。

清点出四处：

| preload 函数 | 它想碰的页面对象 | 隔离后的实际后果 |
|---|---|---|
| `setupToastOverride` | `window.showStatusToast` | 页面 toast 调不到宿主 → 停在「假成功」 |
| `suppressVoiceToast` | `window.showVoicePreparingToast` 等 3 个 | 语音准备提示压不住 |
| `setupVoiceToastOverride` | 同上 3 个（真实实现） | 同上 |
| `setupSettingsSync` | 读 `window.appState` / `window[k]`，写 `speakerGainNode.gain`、`subtitleBridge`、`appProactive`；且 hook `window.saveNEKOSettings` | 设置同步**双向全断**：页面改了不广播，宿主下发不落地 |

修法（两步，缺一不可）：

1. **preload 侧只暴露原语**（结构化克隆安全，只有函数与纯数据）：
   `nekoPageToastBridge`、`nekoPageVoiceToastBridge`、`nekoPageSettingsSync`
   （`onSync` 注册回调 / `broadcast` / `request`）。
2. **页面侧 shim**（`electron-page-bridge.js`）把原语接回页面全局与业务对象：
   - toast：`Object.defineProperty` 装 getter 返回桥实现、setter 吃掉页面迟到赋值，
     并在 `0/100/500/1500/3000 ms` 与 `DOMContentLoaded` 重复安装（页面脚本加载顺序不可控）；
   - 设置同步：`collectSnapshot()`（优先 `appState`，回退 `window[k]`）、`applySnapshot()`
     复刻 preload 接收侧的四个副作用、`onSync(applySnapshot)`、hook `saveNEKOSettings`，
     `role === 'chat'` 时在 `DOMContentLoaded + 1s` 发 `request()`。

未隔离窗口 / 浏览器直开时这三个桥都不存在，shim 首行直接 return，preload 仍走旧路径——
这就是非隔离臂的回归意义（§3 第二行）。

  "settingsBroadcast": true, "settingsEchoSent": true, "pass": true

- `rawSendCount` 来自主进程自己监听的 `ws-raw-send` IPC —— 页面「说」自己走了桥没用，主进程收到才算。
- `settingsEchoSent`：页面广播 `{textGuardMaxLength: 4242}` → 主进程转回 SYNC → 页面

  证明「页面 → preload → 主进程 → preload → 页面」整圈闭合。

## 6. 聊天往返：试 Qoder 的模型（结论：没走这条路）

目标是想让 Chat 窗真的把一句话发到模型再收回来。探查结果：

- 本机 `~/.qoder-cn` 下**没有**可复用的本地模型服务；`QODER_SDK_AUTH_PAYLOAD_FILE`
  指向的文件不存在；`QODER_SDK_CUSTOM_BASE_URL_BYOK` 是 1 字符开关，不是 URL。
- 日志里唯一的对话端点是
  `https://gateway.qoder.com.cn/algo/api/v2/service/pro/sse/agent_chat_generation`
  —— 私有 **SSE agent 协议**（另有 `/api/v2/model/list`、`/algo/api/v5/service/region/endpoints`），
  **不是 OpenAI 兼容**，不能当 base_url 直连，也没有可文档化的请求体。
- 要「反代」就得从系统安全存储里抽账号凭据、再复刻私有协议：属于账号/ToS 风险，
  **不做**。

替代路线（任选其一，都不需要动 Chat 窗代码）：

1. **BYOK**：在 NEKO 的 provider 配置里加一个 OpenAI 兼容端点（DeepSeek/通义/OpenAI 等），
   Chat 窗走现有 `/ws` 即可完成真往返；
2. **本地 Ollama**（`http://127.0.0.1:11434/v1`），完全离线，同样是 OpenAI 兼容；
3. **只验运输**：本次工装已用本地回显服务证明
   「页面 → 桥 → IPC → 主进程真 WS → 回显 → IPC → 页面」整圈闭合，
   即 Chat 窗的数据通路已经通了，缺的只是后端的模型端点。
