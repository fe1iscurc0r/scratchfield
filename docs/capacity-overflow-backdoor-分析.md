# S22 Capacity Overflow MoE 后门分析

> 来源：digest-g2-4 2608.25371v1（Capacity Overflow Vision MoE Backdoor：批量依赖执行特性
> 构成供应链后门攻击面，小批量审计安全/大批量激活，76-87% 激活成功率）

## 1. 攻击机制

MoE 的**容量因子（capacity factor）**决定每个专家每批最多处理多少 token。当输入批量
超过容量，**溢出 token（overflow）会被改道**——走一条"容量溢出路由"路径。后门就藏在这条
只在**大批量**才触发的路径里：

- **小批量**：容量未超 → 走正常路由 → 行为干净（审计/评测通过）。
- **大批量**：容量溢出 → 溢出 token 走被植入的后门逻辑 → 恶意行为激活（76-87% 成功率）。

本质：后门的触发条件是**批量大小**，而常规安全审计用小批量 → 天然查不出。

## 2. 供应链审计的启示

- **审计批大小必须覆盖生产实际**：只用小批量做安全评测会系统性漏掉批量依赖后门。
- **溢出路径是独立攻击面**：capacity overflow 路由本身需要单独审计（后门最爱藏身的不常走路径）。
- **"边界行为"应纳入测试**：容量边界附近（恰好溢出/不溢出）的行为差异是后门检测的探针。
- **激活率 vs 批量曲线**：批量依赖后门呈"阈值式激活"，审计应扫描批量维度而非单点。

## 3. 审计建议

1. **多批量扫描审计**：评测集覆盖 [1, 2, 4, ..., 生产批量] 的批量档位，比对输出分布差异，检测阈值式激活。
2. **溢出路由专项检查**：对 overflow 分支单独做后门扫描（该分支小批量永不执行，必须显式触发）。
3. **容量因子与路由一致性校验**：记录运行时 capacity 占用与溢出率，异常（正常输入却高频溢出）即告警。
4. **供应链溯源 + 签名**：checkpoint 走 `mcpserver/trust_layer.py` 的 signature/lineage 校验，阻断未审计模型直入生产。
5. **行为差分测试**：同一模型在"小批量 vs 大批量"下对同一输入的输出应一致，不一致即视为可疑（对齐 S17 的参考偏差检测思路）。

## 4. 对 NEKO / 本地 MoE 部署的落点

NEKO 若部署 MoE 系本地 LLM：把"批量大小"纳入模型安全验收矩阵，上线前做多批量差分审计；
容量溢出路径单独走签名/一致性门控。
