## 1. 为什么做这件事

NEKO 现在是一只「死皮肤」桌宠：形象变化只由对话情绪驱动，**不知道 agent 在干什么**。
vibe-pet 的做法证明另一条路可行：把 agent 的真实运行态（思考中/用工具/等审批/完成/报错）
投影成形态变化——桌宠从"装饰"变成"可观测的 agent 状态面板"。

本 SPEC 定义 **Lumo 侧事件 → NEKO 侧动画触发器** 的映射契约。
两侧解耦：Lumo 只负责发标准事件，NEKO 只负责按事件换形态。

## 2. 事件词表（Lumo → NEKO）

事件名用 `<域>.<动名词>` 命名（与仓内 EventBus v2 的 Topics 命名规范一致）。

| 事件名 | 语义 | 触发条件 | 优先级 |
|---|---|---|---|
| `agent.busy` | agent 正在干活 | 工具循环进入新一轮 / LLM 流式输出中 | 中 |
| `agent.idle` | agent 空闲待命 | 工具循环结束且无排队任务，持续 > 30s | 低 |
| `agent.error` | agent 出错 | 工具连续失败 ≥2 轮 / LLM 网关报错 / 未捕获异常 | **高（抢占）** |
| `agent.tool_use` | 正在调用工具 | 单个工具开始执行（含工具名） | 中 |
| `agent.waiting_approval` | 等待人工确认 | HIL 判定 need_confirm / 写操作确认门挂起 | 中（需人注意） |
| `agent.completed` | 任务完成 | 工具循环正常收敛（含总结轮产出） | 中（短暂庆祝） |
| `token.high` | token 用量告警 | 单会话累计超阈值（默认 80% 上下文窗口） | 低-中 |
| `cron.fired` | 定时任务触发 | dogtag scheduler tick 命中任务 | 低 |

上游对照（vibe-pet 五态 → 本表）：

| vibe-pet 状态 | 本 SPEC 事件 |
|---|---|
| thinking | `agent.busy` |
| tool use | `agent.tool_use` |
| waiting for approval | `agent.waiting_approval` |
| completed | `agent.completed` |
| error | `agent.error` |
| （无） | `agent.idle` / `token.high` / `cron.fired`（本仓扩展） |

## 3. 事件源（数据从哪来）

四个**事件源**，全部已在仓内存在，无需新建采集层：

| # | 事件源 | 提供的事件 | 落点（实测存在） |
|---|---|---|---|
| 1 | **事件总线**（EventBus v2） | 全部事件的标准出口 | `apiserver/event_bus/`（`get_bus()` + `Topics`），本轮新增 `Topics.DEVICE_STATE_CHANGED` 即同机制 |
| 2 | dogtag scheduler 状态机 | `cron.fired` / `agent.busy`（任务推进） | `apiserver/task_flow.py` + `Topics.SCHEDULER_TICK` |
| 3 | Hermes cron 触发记录 | `cron.fired`（含任务名） | `~/.hermes/cache/` 下的任务记录（与 W136 日报管道同源） |
| 4 | 工具循环 + token 计量 | `agent.*` / `token.high` | `apiserver/agentic_tool_loop.py`（round_start/round_end/tool_results 已有 SSE 事件）+ `llm_router` 用量 |

**投影通道选择**（三选一，按实现成本排序）：

1. **推荐**：Lumo 把上述事件 emit 到**事件总线** → 新增一个消费者把事件转成
   `POST /api/lumo/event` 反向事件（该端点已存在：`apiserver/routes/lumo_event.py`）
   → NEKO 侧订阅。**零新增传输层**，复用既有反向事件通道。
2. 直接 SSE：复用 agentic loop 已有 SSE 流（`round_start`/`tool_results`/`round_end`），
   NEKO 前端直连。缺点：需要 NEKO 侧维持 SSE 连接。
3. 轮询 `GET /api/device/state`（W131-05 已落地）：最省事但延迟高，仅作降级。

## 4. NEKO 侧动画/表情触发器契约

NEKO 收到事件后按表执行（**形态名称为建议值，具体资产由 NEKO 前端线定**）：

| 事件 | 触发动作 | 持续 | 可打断 |
|---|---|---|---|
| `agent.busy` | 切换到「工作」循环动画（如敲键盘/思考气泡） | 持续到下一个状态事件 | 是（被高优先级抢占） |
| `agent.tool_use` | 「工作」动画 + 工具气泡（显示工具名） | 单次 3s | 是 |
| `agent.waiting_approval` | 「举手/张望」动画 + 提示音（一次性） | 持续到用户响应 | 否（需人注意） |
| `agent.completed` | 「比耶/转圈」庆祝动画 | 2.5s 后自动回落 `agent.idle` | 是 |
| `agent.error` | 「摔倒/冒烟」动画 + 红色状态点 | 5s 后回落 `agent.idle`（红点保留到下次成功） | 否（抢占一切） |
| `agent.idle` | 待机呼吸/眨眼循环 | 持续 | 是 |
| `token.high` | 状态栏进度条变黄 + 轻提示 | 持续到会话重置 | 是 |
| `cron.fired` | 短暂抬头（<1s），不打断当前动画 | 1s | — |

**多 agent 分卡**（借鉴 vibe-pet 的 multi-agent pet view）：
每个活跃会话/子代理一个独立状态槽，UI 上并排显示（如 3 个小形态），
而不是把多个 agent 的状态揉成一个——避免"到底谁在忙"的歧义。

## 5. 去抖与优先级规则

1. **同类去抖**：同一事件 1s 内重复 emit 忽略（防 LLM 流式 chunk 刷爆）。
2. **优先级**：`agent.error` > `agent.waiting_approval` > `agent.completed` >
   `agent.busy`/`agent.tool_use` > `token.high` > `cron.fired` > `agent.idle`。
3. **状态回落**：所有瞬时事件（completed/error/cron.fired）到期自动回落
   `agent.busy`（若循环仍在跑）或 `agent.idle`（循环已停）。
4. **错误保留**：`agent.error` 的红色状态点在下次 `agent.completed` 前不移除——
   错误不该被下一次忙碌无痕覆盖。
5. **静默期**：用户手动关闭行为投影后，Lumo 停止 emit（开关状态落 config）。

## 6. 事件载荷（Payload 契约）

```json
{
  "event": "agent.tool_use",
  "session_id": "sess-abc123",
  "agent_id": "main",
  "ts": 1789999999.123,
  "detail": {
    "tool": "file_edit",
    "round": 3,
    "ok": true
  }
}
```

- `event`：第 2 节词表里的名字（**唯一必填**）
- `agent_id`：多 agent 分卡的槽位键（缺省 `"main"`）
- `detail`：可选，按事件类型不同（`token.high` 带 `used`/`limit`；
  `cron.fired` 带 `task_name`）
- 敏感字段禁入（不传 LLM 原文、不传文件内容——载荷只做状态投影）

## 7. 实现分工与验收

| 侧 | 做什么 | 不做 |
|---|---|---|
| Lumo（后端） | 按第 3 节把事件 emit 到**事件总线**；新增投影消费者转 `POST /api/lumo/event`；去抖/优先级在 emit 侧实现 | 不碰渲染 |
| NEKO（前端） | 订阅事件 → 按第 4 节切形态；多 agent 分卡 UI；状态回落计时器 | 不改 NEKO 上游引擎逻辑（只加订阅层） |
