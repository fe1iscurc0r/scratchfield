# 卷149 悬浮窗"按住不放开窗膨胀 + 黑块填充"—— 修复说明与真机复测清单

> 修复：2026-09-23　　复测人：＿＿＿＿　　复测日期：＿＿＿＿
> 关联：`frontend/electron/modules/floatingStateMachine.ts`（新增）、`window.ts`（改造）

---

## 一、症状

悬浮窗按住不放 → 窗口越来越大 → 增大区域被黑色块不断填充。

## 二、根因（代码实测，非推测）

**统一表述：悬浮态窗口的尺寸约束没有单一权威来源，且缺少"实际尺寸偏离期望就收敛"的机制。**

拆成四条：

### 1. `minimumSize` 被设为"动画目标高度"而非该态的最小值（★ 主因）

`expandFloatingWindow` 的动画回调里：

```ts
// 旧代码
animateBounds(win, fromBounds, toBounds, () => {
  win.setMinimumSize(EXPANDED_WIDTH, targetHeight)   // targetHeight = INITIAL_FULL_HEIGHT(200)
})
```

而动画结束后渲染层 `fitHeight` 会把高度收缩到内容的真实高度（可低至 `MIN_FIT_HEIGHT = 100`）。

⇒ 出现 `minimumHeight(200) > bounds.height(100)`。
**Windows 对最小尺寸大于当前尺寸的窗口会强制放大到 minimumSize** —— 这就是"被撑大"的直接机制。

### 2. 动画被拖拽打断时状态撕裂

`setWindowPosition` 在悬浮态会 `cancelCurrentAnimation()`，而旧 `animateBounds` 的取消路径**只 `clearInterval`，不调用 `onDone`**：

```ts
// 旧代码
cancelCurrentAnimation = () => {
  clearInterval(interval)
  cancelCurrentAnimation = null      // ← 没有 onDone：约束停在动画起始态
}
```

⇒ 动画开始时设的 `setMinimumSize(BALL_SIZE, BALL_SIZE)` 被永久保留，而窗口尺寸已处于动画中间帧，约束与真实 bounds 不一致。

### 3. 缺少"偏离期望就纠正"的收敛机制

任何外部尺寸变更（原生 resize / Electron 平台缺陷）都会被**保留并累积**，没有任何兜底。

### 4. 渲染层 fitHeight 无趋势守卫

`_lastFitHeight` 只挡"相同值"，挡不住**递增环**：
窗口变大 → 测量容器 `scrollHeight` 变大（flex/overflow 依赖视口）→ `desired` 变大 → 窗口再变大 → …

## 三、修复内容

| 文件 | 改动 |
|---|---|
| `electron/modules/floatingStateMachine.ts` | **新增**：几何状态机（纯函数）。`computeFloatingGeometry` 成为尺寸/约束的唯一计算入口，保证不变式 `minWidth<=width && minHeight<=height`；含 `FitHeightTrendGuard` 趋势守卫 |
| `electron/modules/window.ts` | 所有 `setMinimumSize`/`setResizable` 收敛到 `applyFloatingConstraints`；动画取消路径补 `syncConstraintsToCurrentBounds`；**新增期望尺寸守卫**（`resize` 事件检测偏离并强制纠正）；动画期间约束取起止尺寸较小值；`invalidate()` 缓解黑块 |
| `electron/main.ts` | 新增 `floating:setDragging` IPC；`window:setBounds` 补悬浮态守卫（该通道的 `Math.max(800,...)` 下限会把悬浮窗撑到 800×600） |
| `electron/preload.ts` | 白名单 + API 增加 `floating.setDragging` |
| `src/electron.d.ts` | `FloatingAPI` 补 `setDragging` 类型 |
| `src/views/FloatingView.vue` | 拖拽时通知主进程（双保险）；`fitWindowHeight` 加趋势守卫；卸载时解除拖拽冻结 |
| `tests/floatingStateMachine.test.ts` | **新增** 17 个用例（含"minHeight 不得高于 bounds"的直接回归） |

### 主动加的防御（工单未要求，但同源）

- **动画期间约束取起止尺寸较小值**：否则 `ball → full` 动画开始前 `minWidth=420` 会让 Windows 把 100 宽的窗口**立即弹到 420**，造成跳变。
- **`commitExpectedBounds` 先于 `setBounds`**：否则 resize 事件若即时派发，守卫会拿旧期望值误判偏离、把窗口纠正回去。
- **`invalidate()` 延后一个 tick**：否则重绘的还是旧尺寸的合成结果。

### 日志观察

复测时留意 DevTools / 主进程控制台，出现以下任一即为**守卫生效**（非故障）：

```
[floating] 检测到尺寸偏离：实际 WxH ≠ 期望 WxH，已强制纠正
[floating] fitHeight 连续递增 N 次，判定反馈环，本次 fitHeight(H) 已忽略
[floating] 几何不变式违规（state=xxx）: ...
```

- 前两条偶发出现 = 守卫在按设计工作；
- 若**高频刷屏**，说明仍有路径在持续改尺寸，需带日志回来复诊。
- 第三条（不变式违规）**不应出现**，出现即为状态机有漏。
