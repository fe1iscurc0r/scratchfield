# 包描述与协商层 · 勘察与判断 · 2026-09-29

> **缘起**：决定做法律包之后浮现的一个问题——**mechat（机械操控）是否也要插件化？**
> 提出者判断这「其实就是另一个版本的 dsh 问题」。
>
> **本文定位**：不写实现，只给**事实盘点 + 判断 + 落点建议**。结论先行，证据带路径。
> **相关**：`docs/dsh-生态-新标准-勘察-2026-08-26.md`（dsh 元协议勘察）、
> `docs/领域包指南.md`（域包机制）、`docs/机械操控编排-W130-总体架构-2026-09-18.md`（mechat 架构）。

---

## 一、结论（先给判断）

1. **mechat 该可插拔，但归口不是「域包」**——它是**能力包**（capability pack），
   与域包（domain pack）是两类东西：前者扩展「能做什么」，后者扩展「记录什么」。
2. **真正缺的不是给 mechat 加开关，而是「包描述与协商层」**。现状是**两套平行机制、各缺一半**
   （域包有声明无能力/依赖，MCP agent 有能力无依赖/预检）。
3. **dsh 里最该抄两条：静态 manifest 预检 + 声明式协商**。而这两条在 **mechat 上比法律包更刚需**——
   法律包装错只错表单，机械包装错可能让舵机越限。**硬件类包的安全预检是必要条件，不是体验优化。**
4. **我们缺 Facet 槽位**：域包只能改 ELN 表单字段；机械要的是「状态卡片 / 控制面板」。
   「一个包含多面能力、宿主只激活所需」的机制目前无处安放。

## 二、现状盘点（实测）

### 2.1 两套平行机制的能力矩阵

| | 有声明 | 有能力声明 | 有版本 | 有依赖/硬件要求 | 有启用控制 | 有装前预检 |
|---|---|---|---|---|---|---|
| 域包 `domains/<n>/pack.yaml` | ✅ | ❌ | ❌ | ❌ | ❌（靠目录存在） | ❌ |
| MCP `mcpserver/<n>/agent-manifest.json` | ✅ | ✅ | ✅ | ❌ | ❌ | ❌ |

- 域包声明块只有四个：`eln.fields` / `papers.id_fields` / `source_presets` / `tagging.questions`
  （出处：`docs/领域包指南.md` §1 的表）。
- MCP manifest 有 `name` / `displayName` / `version` / `entryPoint` / `capabilities.invocationCommands`
  （样例：`mcpserver/academic/agent-manifest.json`）；全仓 **40** 个 manifest。
- **两者都没有** `requires`（我要什么）与任何形式的装前兼容性判定。

### 2.2 mechat 的现有形态是对的

机械这条线**已经是能力包形态**，不是域包：

```
对话层 Lumo
  │ MCP tool calls
能力层 mcpserver/antenna_rotator/  (agent 目录型：tools.py + agent-manifest.json)
  │ 本地回环
会话层 rotator_daemon  (独占串口 / 双通道仲裁 / E-STOP 抢占 / 状态缓存)
  │ USB CDC / SX1278
执行层 ESP32-S3 固件 (motion/planner + feedback/as5600 + servo_ptz + SafetyGovernor)
```
（出处：`docs/机械操控编排-W130-总体架构-2026-09-18.md` §二）

卷130 决策 1 明确选「daemon 独占串口、MCP 做薄客户端」，理由是**有独立状态/配置**——
按 `docs/mcpserver-工具编写规范.md` §1 归为「agent 目录型」。这条判断与本文结论一致。

## 三、为什么 mechat 不该归域包（本质差异）

| 维度 | 域包（law） | 能力包（mechat） |
|---|---|---|
| 声明的语义 | **记录与检索**的领域差异（字段/主键/来源/打标） | **执行与物理交互**（工具面/会话/安全环） |
| 扩展点 | `pack.yaml` 四个声明块 | `agent-manifest.json` + daemon + 固件 |
| 代码量 | 零（可选 `importers/`） | 必需（会话层、内核、三保险） |
| 运行时依赖 | 无 | 串口 / 驱动 / 固件版本 / 板子在位 |
| 失败面 | 字段配错 → 表单不对 | 链路断或版本不符 → **物理动作失误** |
| 风险等级 | 数据录入错误 | 机械伤害 |

**域包的抽象边界是「数据语义」**。把 `rotator_move` / `rotator_estop` 塞进 `eln.fields` 是不可能的——
这不是抽象不够好，而是**扩展点类型不同**。强行合并会逼出 `if domain == "mechat"` 之类的分支，
直接违反域包机制的核心原则（`docs/领域包指南.md` §1：「核心代码中不出现任何 `if domain == ...`」）。

## 四、与 dsh 元协议的对应（该抄什么）

dsh-std 的六条（出处：`docs/dsh-生态-新标准-勘察-2026-08-26.md` §二）与我们现状的逐条对照：

| dsh 思想 | 我们的现状 | 是否该抄 | 理由 |
|---|---|---|---|
| 协议即插件（独立版本化） | manifest 有 `version`，但域包没有 | **该抄**（补域包版本） | 与「准入版本基线」同源 |
| 声明式协商（`requires`/`supports`） | 都没有 | **该抄**（最高价值） | 无此则无法在装前判断兼容性 |
| Adapter 单点缓冲 | NEKO 桥（`hermes_proxy`+wrapper）已同思路 | 已具备，保持纪律 | 勘察已确认架构裁决一致 |
| **静态 manifest 预检** | **无** | **该抄**（最高价值） | 把兼容性从运行时挪到装前 |
| **Facet 模型** | **无** | **该抄**（我们缺的槽位） | 域包只能改表单，机械要控制面板 |
| 纯函数核心 | 部分（`domain_pack.py` 是纯读取） | 该保持 | 便于 headless 单测 |

**关键判断：预检的必要性与包的类型相关，且硬件类最强。**

- 域包装错：表单少个字段 → 用户看得见、改一行就好
- 能力包装错：`rotator_status` 返回 `ok=False, error="daemon_unreachable"`（`docs/机械操控编排-W130` §4.1 的降级语义）
  → 用户已经装了、已经点下去了，才发现链路不通

所以「**不跑一行代码就知道装不装得炸**」这条，对 mechat 是**安全问题**而非体验问题。

## 五、建议落点（按优先级，均建议独立成卷）

### 5.1 第一步：给 manifest 加 `requires` + CI 静态预检（低风险、立刻可用）

- 在 MCP manifest 增加 `requires` 块，声明：Python 依赖 / 系统可执行 / 硬件（串口、设备）/ 固件版本区间
- 写一个 CI 校验脚本（纯静态，不 import）：毫秒级输出兼容性报告
- 直接收益：回答「**哪些 agent 该默认加载**」——目前 40 个 manifest 全量存在，
  其中安全/逆向类（`agent_frida`/`agent_nuclei`/`agent_trivy`/`agent_decompile`/`agent_osint`/`agent_pentest`/`agent_sbom`/`agent_signing`）
  与普通科研工作流无关，**默认全加载本身就是启动开销 + 攻击面 + token 消耗**。
  这与 mechat 是同一个病：**缺「按需装配」的表达能力**。

### 5.2 第二步：统一 kind 命名空间（域包与能力包并列）

- 两者共用同一套协商字段，但 `kind` 区分：`domain`（数据语义） / `capability`（执行能力）
- 保留各自的专属声明块（域包的 `eln`，能力包的 `capabilities`）——**不合并抽象，只统一外壳**
- 域包顺带补 `version`，为将来的准入基线留位

### 5.3 第三步：机械类包的 `safety` 声明独立成块（安全必需）

不能与普通工具混在一张表里。至少声明：物理限位、急停能力（`rotator_estop` 属「任何通道都不得降级」类）、
fail-safe 策略（卷130 决策 3 定的 `hold_then_disable`，N 可配）。
对齐 `docs/机械操控编排-W130` §4.1 里已定稿的工具面契约。

### 5.4 不做的事（明确边界）

- **不引 dsh 代码**：TS 栈不符（沿用 2026-08-26 勘察的结论）
- **不做运行时协商**：先把兼容性判断挪到装前，运行时协商是更远的事
- **不合并域包与能力包**：扩展点类型不同，合并会逼出领域分支

## 六、与打包边界的联动（同源问题）

本次发布包收刀与本文判断同源：**包的边界该由「它属于谁」决定，而不是「它恰好在仓库里」**。

`naga-backend.spec` 的黑名单据此收紧（实测 `datas` 体积 **4.37 GiB → 117 MiB**）：

| 排除项 | 依据 |
|---|---|
| `NEKO` / `neko-electron-shell` | 上游独立项目，本仓仅含桥接改动（反向事件等） |
| `HamLog` | 第三方项目（GPL-3.0），许可传染风险 |
| `coupled/*` | standalone 插件（自带 `plugin.yaml` + 商业许可） |
| `OpenClaw` | 可选增强，不属发布包 |
| `mod/sources`、`tmp`、`github_haul`、`carpet`、`sitaware-ui/node_modules` | 非运行时（详见 CHANGELOG [5.1.5]） |

**纪律**：改 spec 黑名单 = 改产品边界，必须同步 `build.md` 的边界表与 `CHANGELOG.md`。
