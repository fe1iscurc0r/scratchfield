# 双事件总线关系评估（W100-04）

> 2026-09-08 · 评估（不写实现）· 基于 09-08 体检快照（13 模块无环、双总线并存）

## 一、两条总线拆解

| 维度 | apiserver/event_bus | mcpserver/workflow/event_bus |
|------|--------------------|------------------------------|
| 来源 | Cordis EventsService（还原五种 dispatch） | buzz「事件日志即消息总线」 |
| dispatch | emit / parallel / serial / bail / waterfall | pub/sub 同步分发 |
| 持久化 | 无（内存热插拔注册） | append-only JSONL 事件日志（可回放） |
| 事件域 | 消费者侧：状态/决策事件 | 任务侧：task_created/assigned/claimed/blocked/done/review_* |
| trace | 无内置 | 每事件带 id/timestamp/source/trace_id |
| 依赖 | asyncio（stdlib） | 纯标准库（json/threading/uuid） |

## 二、职责边界裁定

- **apiserver bus = 决策/状态消费者总线**（同步/异步分发语义丰富，服务运行时通知）。
- **workflow bus = 任务生命周期事件账本**（可审计、可回放、trace_id 贯穿）。
- **互不引用**、职责正交：一个管「分发语义」，一个管「事件事实记录」。

**裁定：互补，不冲突，不合并。** 强行统一会同时破坏两边的专长（五 dispatch 语义 vs 事件日志账本）。

## 三、事件拓扑图（谁 publish 谁 subscribe）

```
┌─ 任务侧（workflow bus）────────────────────────────┐
│ mcpserver 调度器 ──publish──▶ task_created/assigned │
│ agent 执行器 ──publish──▶ task_done/review_*        │
│ （JSONL 落盘，trace_id 贯穿一次逻辑操作）            │
└──────────────┬─────────────────────────────────────┘
               │ 桥接点（见四）
┌──────────────▼─────────────────────────────────────┐
│ 消费者侧（apiserver bus）                           │
│ 状态视图/决策模块 ──subscribe──▶ 内部事件            │
│ （emit/parallel/serial/bail/waterfall 内存分发）     │
└────────────────────────────────────────────────────┘
```

## 四、桥接方案（如需 workflow 事件触达 apiserver 侧）

- 方式：workflow bus 的 JSONL 追加处挂一个轻量 adapter，把 `task_done/review_*`
  转发为 apiserver bus 的 emit 事件（带原 trace_id）。
- 工作量：约 0.5 天（一个转发函数 + 两行注册），**本工单不写实现**，留后续批次。

## 五、结论

**互补共存 + 按需桥接**。拓扑图见上；桥接点单一（workflow → apiserver 单向转发），
trace_id 作为贯穿键。
