# SPEC 写作规范 · v2（spec 的 spec）

> 用途：统一所有 SPEC 的写作标准，供 WorkBuddy / Trae / Hermes 写 SPEC 与审 SPEC 时执行。
> 读者：AI 施工方（**不共享写作者的上下文**，SPEC 必须自包含）。
> v2 修订：融入系统工程四原则内核 + harness「不变量伴生」方法论。v1 的十条规则降为「投影」。

---

## 〇、一句话定位

**SPEC 是一份「可校验的施工契约」——用系统工程四原则划界，用 harness 式不变量验收。**

不是计划（给人看的决策依据），不是工单（给 AI 排的任务表）。SPEC 要回答的终极问题是：**「凭什么说这份施工图合格？」答案必须能查，不能靠感觉。**

---

## 一、内核：系统工程四原则 → SPEC 四问

任何一份 SPEC，先过这四问，再谈格式。四问是母体，格式是投影。

| 原则 | 一句话 | SPEC 里落到哪 |
|------|--------|--------------|
| **P3 边界** | 划清边界是分析的第一刀，边界错后面全错 | 「一、背景与边界」做/不做对照表 |
| **P2 层次** | 任何系统都可分层，关键是选对抽象层 | 「二、架构设计」组件分层 +「三、施工步骤」步骤分层 |
| **P1 关系** | 系统的灵魂是关系，不是元素；元素可换，关系才定义系统 | 「二」数据流图 +「四、关键假设」依赖关系 |
| **P4 目的** | 系统有目的，多目标需协调 | 「八、验收标准」可量化目标 |

**自检问题（启动任何 SPEC 前先答）：**
1. 边界：包含什么？排除什么？
2. 层次：在哪个抽象层操作？上/下移一层的代价？
3. 关系：关键接口/依赖是什么？换掉某元素，系统还成立吗？
4. 目的：做完的判据是什么？能跑成一条命令吗？

## 二、方法论：harness 的「不变量伴生」→ 验收即检查

harness（DeepSeek Harness）最值得抄的一条：**架构约束从文档变成可执行检查**——它的 invariant 伴生插件，在运行时把「不该发生的事」变成断言，生产可卸载。

SPEC 的验收标准同理：

- ❌ 纸面声明：`"跑通"`、`"功能正常"`、`"无明显 bug"`
- ✅ 可执行不变量：每条验收 = 一条 `grep` / `assert` / `python -c` 命令

```
# 好例子（验收 = 运行时断言）
1. 三个测试用例 python -c 输出 PASS 1/2/3
2. grep -n "lumo_state" apiserver/routes/lumo_event.py 返回非空（已接线）
3. 原有逻辑未改：git diff 确认仅第 4 步追加
4. 无新增 LLM 调用：grep -n "acompletion" lumo_state.py 返回空
```

**这条方法论把「验收」从人力判断变成机器检查——这才是 SPEC 能成为「可校验契约」的根本。**

## 三、投影：十条规则（v1 保留，精简）

1. **三层文档分离**：计划（给人）/ SPEC（给 AI 施工）/ 工单（排任务），一份只做一件事。
2. **十个必含章节**：一句话定位 → 背景与边界 → 架构设计 → 施工步骤 → 关键假设与 fallback → 已知限制 → 测试用例 → 交付物清单 → 验收标准 → 提交规范。
3. **代码骨架可直接用**：施工方不共享上下文，代码片段要能直接粘贴运行，不能是伪代码示意。
4. **引用到文件 + 行号**：说"改 X 第 4 步"要给出 `X.py:207`，不能只说"某处"。
5. **不写"试试看"**：做不了的写「不能做 + 原因」，迂回路径显式标「迂回」。
6. **每个 LLM 调用点显式声明**：有无 LLM、在哪调、token 开销，写进架构或步骤。
7. **边界用表，不用散文**：做/不做、假设/fallback 用表格。
8. **已知限制诚实标注**：每条含「具体是什么 + 为什么超出范围」。
9. **测试纯 Python 优先**：云服 `python -c` 能过 = 逻辑正确；需真机的单独标「端到端验证」。
10. **命名 + 版本**：`<主题>-SPEC-v<N>.md`，小改追加修订记录，大改升版本号。

## 四、动力学：SPEC 会演化（不是写完就完）

| 概念 | 系统论表述 | 对 SPEC 的启示 |
|------|-----------|---------------|
| **熵增** | 封闭系统走向混乱 | SPEC 会随代码腐化而失真，需定期「蒸馏」——对照代码重写，不是攒着 |
| **稳态** | 扰动后回平衡 | 代码变了 SPEC 没跟上 = 失衡，要触发「SPEC 复审」 |
| **反馈** | 负反馈 = 自纠错 | 施工方卡住 → 回填 SPEC 的「假设与 fallback」，下次不踩 |

**规则**：施工方在照 SPEC 施工时发现「假设不成立 / 步骤对不上 / 验收跑不通」，**必须回填 SPEC**，而不是绕过 SPEC 硬干。SPEC 是活的，靠施工反馈长大。

## 附：本规范的验证方式（审 SPEC 时逐条问）

1. 四问过了吗？（边界 / 层次 / 关系 / 目的）
2. 十个章节齐了吗？
3. 每条验收标准是「可执行不变量」吗？（能 grep / assert）
4. 每条已知限制有「具体 + 原因」吗？
5. 测试用例云服能跑吗？代码骨架能直接粘贴吗？

五条全过 = 合格 SPEC。缺一条 = 打回补。
