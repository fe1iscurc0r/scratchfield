# 总线能力标签体系 · 2026-09-29

> **定位**：陆墨走「一根总线 + 细化分类」，不做特化版本。本文定义总线内的分类结构、
> 落地机制与迁移路径。**不涉及产品分版本**——分类只用于组织、检索、按需装配与安全闸门。
>
> 相关：`docs/aci-tool-registry-勘察报告.md`（S-01 两层模型 App/Function）、
> `mcpserver/tool_registry/meta.py`（S-02 已实现 `categories` / `security_schemes`）、
> `docs/包描述与协商层-勘察-2026-09-29.md`（领域维度的由来）。

---

## 一、为什么需要（实测依据，不是设想）

| 事实 | 出处 |
|---|---|
| **40 个 manifest 里没有任何分类字段** | 字段全集实测：`agentType/author/capabilities/description/displayName/entryPoint/license/name/runtime/source/tools/vendor/version` |
| **大部分能力不属于任何领域** | 逐个归类：领域向约 14 个（compute/instrument/offense），**跨族通用约 27 个** |
| **领域维度在机制里完全不存在** | 有 `vendor`/`source`/`license`，无 `domain`/`family`/`tier` |
| 因此「按领域做任何事」（打包/加载/授权）只能手工列目录 | 参考发布包黑名单的手工维护代价 |

**核心判断**：`headroom` 这类通用技能（LLM 上下文压缩）不属于任何领域，却被和领域能力平铺混放。
**通用能力是内核，领域是外挂**——与 dsh「core 零领域字段」同源。

## 二、四个正交标签

落在 manifest 的 `classification` 块（不新增顶层字段，避免污染既有命名空间）：

```json
"classification": {
  "families": ["context"],              // 干什么 —— 总线内一级组织维度（多值）
  "domains": [],                        // 谁用 —— 空 = 跨领域通用
  "tier": "local-write",                // 谁能开 —— 安全闸门
  "origin": {                           // 怎么来的 —— 「借」的声明 + 许可隔离证据
    "kind": "bridge",                   // native / vendored / bridge
    "upstream_cli": "microsoft/markitdown",
    "upstream_license": "MIT"
  }
}
```

**为什么是标签不是树**：`headroom` 属 `context` 族，但**所有族都用它**；树状会让
27 个通用能力都堆进一个「通用」大节点，或在多个分支重复归属。标签可多值，代价是
**必须有词汇表纪律**（否则退化成垃圾抽屉）→ 见 §五的 CI 校验。

### tier 四档（按底层工具侵入性，不按功能名）

| tier | 判据 | 当前成员 |
|---|---|---|
| `read-only` | 只读查询/计算，无副作用 | weather_time、material_science、chembl… |
| `local-write` | 写本地文件/DB | memory_maas、document_pipe、markitdown |
| `process-control` | 启停进程或驱动硬件 | ptz_service、app_launcher、code_workspace |
| `offensive` | **主动接触目标或注入** | agent_frida、agent_pentest、agent_strix、agent_nuclei |

**`offensive` 默认关闭**（先例：`mcpserver/adapters/vulnclaw.py` 的 `VULNCLAW_ENABLE_INVOKE`；
本批已在 4 个 agent 的入口落地，`*_ENABLE_INVOKE=1` 才开启，实测两态通过）。

> 依据：法律包装错只错表单，机械/网安包装错可能造成实际损害。**`offensive` 一级的安全
> 闸门不能靠领域名兜底**——`vulnclaw`（渗透编排）与 `material_science`（算物性）
> 现在同级加载，风险差几个数量级。

## 三、族词汇表（9 族）

| 族 | 定位 | 成员 |
|---|---|---|
| `context` | 上下文与记忆 | headroom、memclaw、memory_maas、graph_memory_adapter、semantic_web、graphify |
| `document` | 文档与文献 | markitdown、pdf2md_adapter、paper_miner、zotpilot、firecrawl_adapter、context7、agent_animation |
| `code` | 代码工作 | code_workspace、code_review_graph |
| `verbal` | 语音与视觉 | tts_api、voice_mcp_bidi、voice_mcp_minimax、screen_vision |
| `compute` | 科研计算 | academic、chembl、chemmcp、material_science、scikit_fingerprints、bofire、pycalphad、smiles_transformer |
| `instrument` | 仪器与执行 | ptz_service、antenna_sim、rf_brain、rsba1_ic705 |
| `offense` | 安全与情报 | vulnclaw、llm4decompile、sentinel_intel + 本批 11 个（frida/nuclei/pentest/strix/trivy/sbom/signing/runtime/waf/osint/decompile） |
| `ecology` | 生态与系统 | app_launcher、workflow、trace_audit、fault_inject、weather_time、game_guide、cli_anything、hamlog_adapter、agent_browser、agent_reach |
| `semantic` | 领域数据语义（非 agent） | `domains/default`、`domains/law`（域包，见 `docs/领域包指南.md`） |

**族与领域的关系**：`compute`/`instrument`/`offense` 有明确的领域倾向（材料机械网安），
其余六族是跨领域通用。**族是常在的，领域是标注**——同一族可以服务多个领域，
同一领域可以由多个族的包组成（如「机械领域」= `instrument` 族的 4 个包）。

## 四、进度与迁移路径

**已分类 13 / 待分类 42**（2026-09-29 实测）。

| 阶段 | 内容 | 理由 |
|---|---|---|
| ① 已做 | 13 个薄桥 agent（`offense` 族为主） | 侵入性最高、最需要 tier 闸门 |
| ② 建议下一步 | **通用族 27 个**（context/document/code/verbal/ecology） | 最稳定、争议最小，天然无 tier 风险 |
| ③ 最后 | `compute`/`instrument` + 3 个 `tool_registry/*.yaml` | 涉及领域归属讨论 + yaml/json 两套格式 |

**迁移手法**：manifest 逐加 `classification` 块即可（**不必迁移到 meta.yaml**——
两套格式并存不冲突，S-02 的 yaml 是给新工具用的增量方案）。

## 五、落地机制与纪律

### 5.1 装配策略（已实现，2026-09-29）

**分类的第一个消费者**：`apiserver/mcp_assembly.py` + `apiserver/routes/extensions.py`。

`GET /mcp/services` 原本把内置 agent 的 `enabled` **硬编码为 True**（40+ 个全启用）。
现在改为按 `classification` 计算默认值：

```json
// config.json → mcp_server.assembly（缺省 = 全启用，不改既有行为）
{
  "mcp_server": {
    "assembly": {
      "disable_tiers": ["offensive"],              // 默认关掉攻击性档
      "enabled_families": [],                      // 空 = 不限族；填了则只启用选中的族
      "disabled_agents": ["agent_frida"],          // 显式黑名单
      "agent_overrides": { "agent_nuclei": true }  // 用户显式开关（前端 toggle 写这里）
    }
  }
}
```

**优先级**：`agent_overrides`（用户显式） > `disabled_agents` > `disable_tiers` >
`enabled_families` > 默认启用。

两条设计取舍：
- **判定为 disabled 而非不列出**：保留可发现性（用户能看到有什么、知道怎么开），
  且复用前端既有的 `enabled` 字段，**不需要改前端**。
- **未分类的 agent 不参与族过滤**：避免因分类缺失被静默关掉。

**顺带修掉的既有缺口**：`PUT /mcp/services/{name}` 此前只认 mcporter 外部服务，
对内置 agent 直接抛 404 —— 前端那个开关对内置 agent 是坏的（点了报错）。
现在内置 agent 的开关写入 `assembly.agent_overrides`，开关真正生效。

> 单测：`tests/test_mcp_assembly_policy.py`（12 例，纯函数、不依赖 FastAPI）。
> 其中 `test_empty_policy_keeps_everything_enabled` 是**兼容性红线**——
> 无策略时必须全启用，保证引入本模块不改变既有行为。

### 5.2 词汇表纪律

1. **词汇表是唯一真源**：族名定义在 `mcpserver/tool_registry/check_classification.py`，
   manifest 的 `families` 取值必须落在表内。
2. **静态校验**（已实现）：`check_classification.py` —— stdlib only、纯静态，
   毫秒级输出「族名/tier/域是否合法、领域名是否混进 categories、
   tier=offensive 的入口是否含闸门」。覆盖两套格式（agent-manifest.json + meta.yaml）。
   CI 集成本可挂（私有仓 Actions 额度耗尽，暂缓）。
3. **改 tier 等于改安全面**：`tier` 从非 offensive 改成 offensive 时，必须同时确认入口
   有闸门（否则是空洞声明）—— 这条已由校验脚本强制。
4. **`origin.kind = bridge` 是「借」的声明**：本仓只做薄桥、不内嵌上游代码，
   `upstream_license` 记录上游许可——**许可隔离靠进程边界，不靠声明**，
   但声明让审计可查（对齐既有的「融合拓扑审计」台账）。

## 六、已知隐患

**旧实例的 `categories[0]` 被用作领域名**。`mcpserver/tool_registry/*.yaml` 现有三个实例：

```yaml
bofire:              categories: [materials, experimental-design, optimization]
pycalphad:           categories: [materials, thermodynamics, phase-diagram]
smiles_transformer:  categories: [materials, molecular-representation, ...]
```

第一个值全是 `materials`（领域名）。**照这个填法往下走，`categories` 会退化成领域划分**，
与「不做特化」的方向相反。

**处置建议**：迁移这批 yaml 时，把 `materials` 从 `categories` 移到 `domains`，
`families` 填 `compute`；`categories` 保留为细粒度主题词（第二、三个值那种）。

## 七、不做的事（边界）

- **不做领域分版本**（法律版/材料版/机械版）——按既定方向：一根总线 + 细分分类
- **不合并域包与能力包**——扩展点类型不同（数据语义 vs 执行能力），合并会逼出 `if domain == ...`
- **不引 dsh 代码**（TS 栈不符，沿用 2026-08-26 勘察结论）
- **不做运行时协商**——先把兼容性判断挪到装前
