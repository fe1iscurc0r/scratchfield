3. 传输层：为什么它是**可插拔**的（本模块的关键设计）
================================================================================

  ┌─ 离线（本单验证的路径）───────────────────────────────────────────┐
  │  ZhiMcpClient ──send──► LoopbackTransport ──► FakeZhiDevice.inbox │
  │       ▲                        │                                  │
  │       └──recv── LoopbackTransport ◄──deliver── FakeZhiDevice       │
  │  同进程；客户端等待响应时调 `pump=device.serve_all` 驱动假设备       │
  │  ⇒ 全链路（含翻页、-32601、-32602）**不需要硬件也不需要网络**        │
  └───────────────────────────────────────────────────────────────────┘
  ┌─ 真机（调用方提供）───────────────────────────────────────────────┐
  │  ZhiMcpClient ──send──► 调用方的 WebSocket/MQTT 客户端 ──► 设备     │
  │  本模块**不引入** ws/mqtt 库、**不替调用方选型**、**不建立连接**      │
  │  ⇒ 协议层在无硬件无网络的机器上仍可完整回归（这是刻意的）             │
  └───────────────────────────────────────────────────────────────────┘

5. 协议/题材对齐（虚线，无代码耦合）
================================================================================

  zhi_mcp ·························► 78/xiaozhi-esp32 :: docs/mcp-protocol_zh.md
     信封 {session_id,type,payload} + JSON-RPC 2.0 的三个方法；
     ⚠️ 上游文档自述「AI 辅助生成，请参照代码确认细节」⇒ 本实现对未知字段原样透传。

  zhi_mcp ·························► mcpserver/esp32/（243）
     243 是**集群/编码仿真**（分簇 + RLNC 冗余分配），本模块是**设备控制协议**：
     前者算"空口怎么传"，后者管"设备上有什么工具、怎么调"。**不共用代码**。

  zhi_mcp ·························► mcpserver/mcp_registry / mcp_manager
     那是本仓**内部**的 MCP 工具总线（agent 之间互相发现/调度）；
     本模块是**对外**接小智设备的协议层（设备是 MCP 服务器，我们是客户端）。
