## 一、源→目标映射

| 源（lora-mesh，LoRaMesh.ino） | 目标（本仓库） | 映射关系 |
|---|---|---|
| `:11` `uint8_t routes[N_NODES]` 全量路由表数组 | `MeshNode.routes: dest -> next_hop` | 路由表结构对应 |
| `:105` `routes[n-1] = 255` 自身标记 / `:107` next_hop 条目写入 / `:108` next_hop==0 无路由 | `SELF=255` / `install_route` / `route_to` 默认 0 + `no_route` 丢弃 | 路由语义三元组逐一对应 |
| `:158` 发送确认报文 / `:166` 收到下一跳 ACK | `MeshNetwork.acks` 每跳 ACK 记录 | 逐跳确认语义对应 |
| 报文去重（源未显式成表，靠 seq 语义） | `MeshNode.seen: (origin, seq)` 集合 | 泛洪去重显式化（协议设计的补强） |
| 时隙/空口时序（RadioHead 层） | 不实现（纯逻辑模拟） | 明确边界 |

## 二、核心数据结构共鸣（附源行号）

1. **全表路由**：源在每个节点放 `routes[N_NODES]`（`:11`）实现静态路由——本探针以字典形式复刻并保留「255=自身、0=无路由」的哨兵语义（`:105/:108`），这是 LoRa433 点对点升级为多跳互转时最需要借走的设计。
2. **逐跳确认**：源在每跳发送后等待下一跳 ACK（`:158-166`）；本探针 `hops`+`acks` 记录同样把「一跳一确认」变成可断言的协议事实。
3. **TTL 防环**：探针按跳递减 TTL、耗尽显式丢弃并记录原因——静态路由场景下防环靠部署正确性，TTL 是最后防线；该字段在生产固件中应保留。

## 三、难度 × 收益

- 难度：★★☆（纯逻辑模拟 ~110 行 + 3 测试）
- 收益：★★☆（现有 LoRa433 点对点遥控 → mesh 多节点互转的升级路线获得可测协议骨架；2019 停更意味着只提协议设计、不 vendor 代码）

## 四、结论与接入建议（≥3）

1. **升级路线（点对点→mesh）**：第一步沿用现有 433 透传遥控、加「中继节点」转发（路由表静态配置，与探针同构）；第二步再上动态路由（AODV 类）。不建议直接上源仓库固件（停更 + 硬件绑定）。
2. **报文头定版**：`origin + seq + ttl + payload` 四元组进自定义 433 协议帧；去重窗口每节点保留最近 N 个 (origin, seq)——探针 `seen` 集合的固件对应物。
3. **ESP32-S3 + SX1278 落地**：静态路由表存 NVS，节点上电按表转发；ACK 超时 200ms 重传一次（对应 `/166` 语义，但需设重传上限防风暴）。
4. **与边缘自愈联动**：mesh 链路断链可注册为 W102-05 白盒检查项（连续 ACK 缺失 → 触发重连/换路由），两探针字段衔接点：`acks` 缺失计数即健康检查输入。
