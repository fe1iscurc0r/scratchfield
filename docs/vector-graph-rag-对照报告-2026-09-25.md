## 0. 结论先说

| 查询形态 | 纯向量（精确） | 纯向量（ANN 近似） | SQLite FTS5（关键词） | 图遍历（SQL JOIN） |
|---|---|---|---|---|
| **1 跳**（点名找关系） | 1.000 | 1.000 → **0.583**（随规模掉） | **1.000**（延迟最低） | — |
| **2 跳**（迭代扩展） | 0.988 → **0.917** | 0.988 → **0.333** | **1.000** | — |
| **聚合/完整性**（要"全集"） | **0.000** | 0.000 | 0.000 | **1.000** |

三句话：
1. **纯向量能做多跳，但要小心两件事**：① **ANN 近似会随规模掉召回**（IVF-PQ 1 跳 1.000→0.583、2 跳 0.988→0.333 @5000 三元组）；② 迭代扩展会**放大**这个误差。
2. **"纯向量替代图"在本仓的场景里没有免费的午餐**：在这些查询上，本地已有的 **FTS5** 不但不弱，延迟还最低（0.06–0.42 ms）。**向量的收益来自神经嵌入**，不是"向量"这个形式本身（见 §3 边界）。
3. **必须上图（=必须做遍历/连接）的判据是「答案是一个集合」**：聚合类查询上平面检索集合召回 **0.000**，两跳 JOIN **1.000** —— 与卷156 路由表里"聚合类需自建基准"的标注互相印证。

## 1. 参考实现读了什么（不是转述 README，是读源码）

| 项 | 事实 |
|---|---|
| 路线 | **实体与关系都编码成向量**存 Milvus，"用**单次 rerank** 取代迭代式 LLM agent"（README 自述） |

| 检索流程（`graph/retriever.py`） | `_extract_query_entities` → `_retrieve_entities`（实体向量检索）→ `_retrieve_relations`（关系向量检索）→ **subgraph 惰性扩展**（带 `expansion_history`） |
| 默认参数（`config.py`） | `entity_top_k=20`、`relation_top_k=20`、`final_top_k=3`、相似度阈值、**Jev reranker**（`jev_threshold=0.5`） |

**关键观察**：它的"纯向量"仍需要**神经嵌入 + 一次 LLM rerank**（README 示例用 `text-embedding-3-large`）。
所以"零图数据库依赖"成立，但"零模型依赖"不成立 —— 这点对本仓部署成本判断很重要。

## 3. 为什么"召回率"与"可用性"的边界在这里（老实说）

1. **本仓没有神经嵌入**：实验用的向量是**确定性哈希词袋 + TF×IDF**（无外部模型）。首版用无 IDF 的 512 维哈希，1 跳召回随规模从 1.0 崩到 0.24 —— 那是**分桶碰撞/虚词主导**的假崩塌，测的是玩具嵌入的缺陷而不是检索路径差异；加 IDF + 4096 维后才得到上表的公平对照。
2. **合成 KG 与查询共享词表** ⇒ 关键词检索被"喂"得偏强。真实语料里查询措辞与三元组措辞不重合时，FTS5 的优势会缩小，向量（尤其是神经嵌入）的优势会上升。**这个方向的结论本实验不能给**，要真实语料才能定。
3. **因此上表的正确读法**：它比较的是**检索路径**（平面 top-k / 迭代扩展 / 遍历连接）在**同一词表条件下**的行为；**不是**"向量 vs 关键词"的普适胜负。
4. **ANN 近似掉召回是可复现的工程事实**：IVF-PQ 用 16 subquantizer×8bit 压缩，规模上来后近似误差显现；2 跳迭代把误差放大（0.583 → 0.333）。⇒ 若走上游那条路，**必须监控 ANN 参数对多跳的影响**，不能只看单跳。
5. **"聚合类必须上图"的直白解释**：答案是一个集合时，"相关性 top-k"给不出完备性保证；要完备就得**从命中的机构出发做完整性扩展** —— 那已经是在做遍历/连接（本实验用两跳 JOIN 实现，召回 1.000）。平面检索也能靠**循环扩展**逼近它，但循环的**终止条件**（何时算扩展完）就退化成了图遍历问题。

## 4. 落地建议（给本仓）

| 场景 | 建议 | 依据 |
|---|---|---|
| 单跳事实、点名的邻域查询 | **FTS5 就够**（零新增依赖、延迟最低） | §2 表；与卷156 路由表"单点事实走向量/关键词"一致 |
| 已知措辞的高精度匹配 | FTS5 + 现有 `/memory/quintuples/search` | 同上 |
| 语义改写/模糊措辞 | 需要**神经嵌入**（本仓 `apiserver/local_embedder.py` 已有端侧嵌入先例可接） | §3.2 |
| 多跳推理 | 迭代扩展（任一路径）+ **ANN 参数需调**；或直接用两跳 JOIN | §2 表 2 跳列 |
| **聚合/完整性** | **必须走遍历/连接**（本仓 SQLite 足够，不必上 Neo4j/FalkorDB） | 聚合表：0.000 vs 1.000 |

**一句话**：本仓的 KG 检索**不需要图数据库**（SQLite 的连接查询就能覆盖遍历需求），
真正缺的是**神经嵌入**与**聚合查询的完备性路径** —— 前者决定语义召回，后者决定"要不要写成图查询"。

## 5. 未决项 / 边界

1. **未接真实语料**：本实验用合成 KG；用本仓真实五元组（`/memory/quintuples`）复跑是下一步（需先导出快照）。
2. **未接神经嵌入**：哈希词袋 ≠ 神经嵌入；上游 87.8% Recall@5 是"神经嵌入 + LLM rerank"的成绩，**不能归功于向量形式**。
3. **faiss 后端**：本机装了 `faiss-cpu 1.15.1`（PyPI 有 Windows cp312 轮子，装前已核）；milvus 未装（重依赖，按工单"只标注不否决"）。
4. **未做 LLM rerank 对照**：上游的 Jev reranker 需要 LLM 调用，本机无该配置，未跑。
5. **延迟数字的适用性**：都是**内存内小规模**的中位延迟，不含网络/序列化；生产口径需另测。
