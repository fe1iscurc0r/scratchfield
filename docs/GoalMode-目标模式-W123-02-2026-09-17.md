# Goal Mode：目标分解 → 计划展示 → 确认 → 逐步执行（卷123 W123-02）

ZCode 的 Goal Mode 落到陆墨：用户给**目标**，模型先出 **计划**，系统把计划变成**可跟踪任务**，
用户确认后逐步执行，每一步的状态写回 task_store；某步失败就停在那里（fail-closed），
不糊弄过去。

## 对话协议

```
用户：goal: 在工作区加 slugify 并写测试，跑到全绿
  └─ loop 注入目标模式提示（并入 messages[0]，见「system 层合并」）
模型：[PLAN]
      1. 探查：查看工作区目录结构…（工具：shell_exec）
      2. 实现：新建 utils.py 与 tests/test_utils.py（工具：file_write）
      3. 测试：跑 pytest 确认全绿（工具：test_run）
      4. 验证：复核边界与副作用
      [/PLAN]
  └─ 系统：parse_plan_steps → create_task_from_plan → 任务状态 pending（等确认）
            SSE：plan 事件 + task_update 事件
用户：task:confirm   （或前端按钮）
  └─ 任务转 running，注入「当前步骤：sN + 用 [TASK] 报告」提示
模型：（调工具干活）
      [TASK]{"op":"step","task_id":"…","step_id":"s2","status":"done","result_ref":"utils.py:1 新增 slugify","tool":"file_write"}[/TASK]
  └─ record_step_result → 步状态落库 + 轨迹；全部 done → 任务 review（W123-04 审查）
某步失败：
      [TASK]{"op":"step",…,"status":"blocked","result_ref":"1 failed"}[/TASK]
  └─ 任务 status=blocked，**不自动继续下一步**，等用户决定（重试 / 跳过 / task:replan）
```

## 步骤解析

`parse_plan_steps()` 认这些行格式：`1. 探查…` / `- 实现…` / `[ ] 跑测试…` / `[x] …`，
可带 `（工具：file_read）` 标注（解析后从描述里剔除，存进 step 的 `tool` 字段）。

类型判定：**行首显式类型词优先**（`实现：新建 utils.py 并写 tests/…` 算 `code`，
不会被正文里的 "tests/" 抢成 `test`），再退回关键词扫描。

有 `[PLAN]` 标记时按段内解析；没有标记时保守处理——只认列表行，普通句子不算步骤
（避免把日常对话误建成任务）。解析不出步骤则退回默认四步模板。

## 状态机与 fail-closed

| 事件 | 任务状态 |
| --- | --- |
| 按 PLAN 建任务 | `pending`（等确认） |
| `task:confirm` | `running` |
| 步骤 done/skipped，仍有未完成步 | 保持 `running` |
| 步骤 blocked/failed | **`blocked`（不继续下一步）** |
| 全部步骤 done/skipped | `review`（W123-04 开审查；`task_flow.review_enabled=false` 时直接 `done`） |
| `task:pause` / `task:resume` | `paused` / `running` |
| `task:replan <新目标>` | 回到 `pending`（步骤清空重排） |

## 用户指令（元指令在进 LLM 前短路）

`goal:<目标>` · `task:confirm` · `task:list` · `task:continue [id]` · `task:skip <step_id>` ·
`task:replan <新目标>` · `task:pause [id]` · `task:resume [id]` · `task:review [id]` · `task:help`

## system 层合并（复用卷121 的教训）

任务上下文（目标/进度/当前步）与目标模式提示都用
`system.config.merge_context_supplement` **并入 messages[0]**，不追加末尾 system 消息——
上游中继会把「user 之后的 system」拼进 user 消息，模型会当成提示词注入而拒答。
新增事件：`plan`（计划文本）、`task_update`（步状态落库结果），前端按需渲染。

## 实测（`tools/e2e_task_flow.py`，真实 LLM + 真实沙箱）

```
阶段1 [PLAN] 事件（4 行） → task_update: plan_task, steps=4, status=pending
      任务 e90dd601… 状态=pending
        [pending] s1 (explore) 探查：查看工作区目录结构…
        [pending] s2 (code)    实现：新建 utils.py 与 tests/test_utils.py
        [pending] s3 (test)    测试：运行 pytest 确认全绿
        [pending] s4 (verify)  验证：复核边界与副作用
task:confirm → 计划已确认，任务进入执行（running）
阶段3.1 shell_exec ×3 探查 → [TASK] s1 done
         file_write ×2 被卷121 确认门拦下（等待用户确认）
阶段3.2 （确认后）file_write ×2 落盘 → test_run：passed=6 failed=0
         → file_read ×2 + shell_exec + code_exec 复核行为
阶段3.3 [TASK] s2/s3/s4 done → 任务 status=review
```

## 配置

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `task_flow.enabled` | `true` | 关闭后不解析 `[TASK]`、不按 PLAN 建任务 |
| `task_flow.step_template` | 空 → 内置四步 | `type:描述` 每行一条 |
| `task_flow.verify_audit_only` | `false` | 验证门只记不拦（W123-03） |
| `task_flow.verify_max_retries` | `2` | 验证失败允许的修改重试次数（W123-03） |
| `task_flow.review_dir` | `docs/task-reviews` | Review 报告目录（W123-04） |
