# WO-08: 记忆层对照评估（mempalace vs mem0 vs NEKO）

> 日期：2026-08-22 晚 | 委托：实验田维护者自做 | 状态：✅ 完成
> 模式：API 直读，不 clone 大仓

## 一、三系统对照表

| 维度 | mempalace (MIT) | mem0 (Apache-2.0) | NEKO 记忆层 (48912 关) |
|------|----------------|-------------------|----------------------|
| **存储哲学** | 原文逐字（verbatim），不总结不抽取 | 结构化记忆项（抽取+更新） | 分块索引（SQLite+FTS） |
| **检索** | 语义搜索 + 宫殿结构化 scoping | 混合检索（语义+BM25+实体匹配并行融合） | FTS5 关键词 + 向量（bge-small-zh） |
| **分层** | 宫殿：wings(人/项目)→rooms(主题)→closets(压缩索引)→drawers(原文) | short/long/working 三层 + episodic/semantic 分类 | 记忆库分层（本地 SQLite） |
| **索引压缩** | AAAK（名字/词/概念→AI 可读简写，索引卡指向 drawer） | 实体抽取 + 图谱关联 | chunk 级索引 |
| **写入方式** | 后台 hooks 静默写入（subagent 后台跑，不进 chat token） | 显式 add() API / 自动捕获 | 显式写入 |
| **Benchmark** | **96.6% R@5 raw on LongMemEval**（zero API calls） | 94.4 LongMemEval（+27 vs 基线 67.8） | 未测 |
| **后端** | ChromaDB 默认，backend 接口可插拔 | 多种向量库 + 托管平台 | SQLite + 本地 bge-small-zh |
| **成本** | 本地优先，0 API 调用 | 默认 OpenAI embedding（有本地替代） | 纯本地 |
| **灵感来源** | Zettelkasten（卢曼索引卡） | 生产级 Agent 记忆 | 自研 |

## 二、NEKO 差距清单（≥3 条）

1. **无压缩索引层**：mempalace 的 AAAK / mem0 的实体抽取都能"扫一眼就知道在哪"，NEKO 只有关键词+向量，长会话主题漂移后召回弱
2. **无后台静默写入**：mempalace v4 的教训是 hooks 在前台耗 token（$1.13/会话），NEKO 写入走显式路径，会话内记忆同步有延迟
3. **无混合检索**：mem0 语义+BM25+实体三路并行融合，NEKO 的 FTS5 与向量是两套独立路径未融合（还踩过 FTS5 保留字符 bug）
4. **无记忆更新机制**：mem0 会对旧记忆做合并/过期，NEKO 只增不改，长期运行有冗余

## 三、升级建议

### 短期（低风险，直接做）
- **混合检索融合**：NEKO 查询 = FTS5 结果 + 向量结果 双路并行，RRF 融合排序（≈100 行）
- **AAAK 式压缩索引**：给 SQLite 加一张 `index_cards` 表，会话关键名词/主题写入压缩卡片，检索时先查卡片再定位 chunk

### 中期（评估后做）
- **后台写入 hook**：参考 mempalace 把"会话摘要→记忆库"改成后台 subagent 处理，不进聊天 token 流
- **记忆更新/过期**：给记忆项加 `last_access` + 置信度，低频记忆降权或合并

### 决策依据
- mempalace 的"宫殿分层 + 原文存储"更贴近 NEKO 的科研知识库场景（原文准确性重要）
- mem0 的"混合检索 + 实体抽取"更贴近对话记忆场景
- **推荐**：NEKO 主仓走 mempalace 思路（分层+原文），检索层吸收 mem0 的混合融合——两个都不整包抄，各取一半
