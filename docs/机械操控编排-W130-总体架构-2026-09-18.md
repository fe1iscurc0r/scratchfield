## 一、卷129 留下的三个接口接缝（＝卷130 的着手点）

卷129 是刻意留了接缝的，卷130 就是在这些接缝上接东西——不是另起炉灶：

| 接缝 | 卷129 现状 | 卷130 要接什么 |
| --- | --- | --- |
| `ReplTransport` / `MotionCommandSink` | 只有内存实现（上机自检用） | `SerialTransport`（USB CDC）、`LoRaTransport`，命令面真正接上物理链路 |
| `AngleSource`（可注入） | 自检用 `SyntheticSource` | 真机接 I2C，并把编码器读数接进状态上报 |
| 三保险 | 三环分散在三个 header，各自独立 `set_fault` | 收敛为一层 `SafetyGovernor`，统一优先级、恢复语义与上报 |

**三保险的确切落点**（卷130 要整合的就是这三处，出处已核对）：

| 环 | 落点 | 触发语义 |
| --- | --- | --- |
| ① 编码器闭环 | `feedback/as5600.hpp`（文件头标注「第一环」） | 读失败 / 抖动超阈 → 闭环降级 |
| ② 电流堵转 | `servo_ptz/servo_axis.hpp`（ADC 超阈，标注「第二环」） | → `fault`，**必须显式 `ClearFault()`** |

## 三、四个架构决策（已定稿）

> 用户授权「自己做掉」，故下列四条**由实现者按建议拍定并落地**，不再是待确认项。
> 每条都写明了理由与代价，改起来是改一处配置而不是重写。

### 决策 1：串口持有者 —— daemon 独占，**不**让 MCP 进程直连串口 ✅ 已采用方案 B

串口是独占资源，且卷130 有**两个**入口（USB 有线 + LoRa 无线）会同时想说话。

- **方案 A（MCP 进程直开串口）**：少一个进程，但串口独占逻辑、重连、双通道仲裁都会长在 MCP 进程里；
  MCP 重启 = 云台失联；两个工具同时调用会争端口。
- **方案 B（daemon 独占，MCP 做薄客户端）** ✅ **建议**

选 B 的理由：(a) 串口独占与断线重连只该有一处实现；(b) 双通道仲裁必须有个"会话持有者"；
(c) 与既有 sidecar 思路一致（`antenna_sim/sim_exec.py` 就是子进程执行 + 路径收敛）；
(d) MCP 进程重启不影响云台会话。

### 决策 2：LoRa 帧 —— 扩展 dcp，**不**新造帧 ✅ 已采用

本仓已有两套对齐过的帧可复用：`firmware/dcp_lora/dcp_frame.h`（与 `mcpserver/rf_brain/dcp/frame.py`
逐字节兼容）与 `firmware/loracanary/loracanary_frame.h`。

dcp 帧现状（已核对源码常量）：`magic(2B 0xD0CC) + type(1B) + seq(2B LE) + payload(N≤42) + crc(2B LE)`，
总长 ≤49B，**CRC-16/MODBUS**（poly 0x8005 / init 0xFFFF / refin=refout=true，
标准向量 `"123456789"` → `0x4B37`）；type 表已有 `REPORT 0x01 / COMMAND 0x02 / ACK 0x03 / HEARTBEAT 0x04`。

**建议**：遥控链路**直接复用 dcp 帧**，只在 type 表上扩展云台专用类型（不新建 magic、不改 CRC 约定）。
理由：编解码在 C/Python 两侧已对齐且带标准测试向量，新造帧等于把这套校验重做一遍。

### 决策 3：失联后的安全姿态 ✅ 已定：**停住 + N 秒后卸载使能**（`hold_then_disable`，N=30）

链路心跳超时后云台该做什么，三种策略互斥：

| 策略 | 优点 | 风险 |
| --- | --- | --- |
| **停住**（保持位置与励磁） | 最保守、姿态可控 | 长时间保持可能持续堵转发热 |
| **回中**（方位 0 / 俯仰 0） | 姿态可预期、便于人工接管 | 失联时自动运动，本身是一种风险 |
| **卸载使能**（断电松开） | 舵机/步进不着电 | 天线可能因重力或风载自由转动 |

**定稿**：默认 **停住 + 超时 N 秒后卸载使能**，N 可配置（`$FS=<code>,<hold_s>`，默认 30s）。
策略是**四选一**（`hold` / `hold_then_disable` / `center` / `disable`），主机连接时下发，设备自己执行。

> **实现时发现的一个架构要点**：失联策略的**执行者只能是固件**——链路断了主机
> 根本发不出命令。所以主机这条 `$FS=` 只是"约定策略"，真正的判定与执行在设备侧看门狗里。
> 主机只负责记录，并把"按策略此刻设备应当处于什么状态"算出来供重连后核对。

### 决策 4：卷130 是否包含 LoRa 遥控端固件 ✅ 已定：**不含**

**定稿**：本卷只做**主机侧桥 + 协议定义**（`lora.py` 与 `net/lora_transport.hpp`），
遥控端固件（第二颗板子）留到下一卷。理由：本卷不该被"硬件是否到位"卡住——
现在协议已定、两侧编解码已在，遥控端任何时候都能补上而不用改本卷任何代码。

## 四、接口契约（先定下来，实现照此写）

### 4.1 MCP 工具面（`mcpserver/antenna_rotator/`）

工具名一律带 `rotator_` 前缀；成功 `{"ok": True, ...}`，失败 `{"ok": False, "error": "人读原因"}`，
**永不抛错**（照 `docs/mcpserver-工具编写规范.md` §4）。

| 工具 | 参数 | 返回业务字段 | 降级 |
| --- | --- | --- | --- |
| `rotator_status` | — | `az_deg / el_deg / state / fault_ring / link` | 链路不通 → `ok=False, error="daemon_unreachable"` |
| `rotator_move` | `az_deg, el_deg, feed_deg_s=?, accel=?, use_s_curve=?` | `accepted, planned_ms, segment_count` | 越限 → `ok=False, error="error:limit"`（回显与固件一致） |
| `rotator_home` | `axis="both"\|"az"\|"el"` | `homing_ms` | — |
| `rotator_estop` | — | `ok` | **任何通道都不得降级为"稍后重试"** |
| `rotator_gcode` | `line: str` | `ok / error:limit / error:unknown` | 直接复用 W129-04 回显语义 |
| `rotator_calibrate` | `axis, lo_deg, hi_deg` | `travel_lo/hi, max_residual_deg, note`（含「磁铁偏心」提示） | 无编码器 → `ok=False, error="as5600_absent"` |
| `rotator_link` | — | `transport, rssi_dbm, last_hb_age_s, failsafe_policy` | — |

**关键约定**：`rotator_move` / `rotator_gcode` 的 error 文本**必须与固件回显逐字一致**
（`error:limit` / `error:unknown`）——Lumo 侧才能用同一套字符串做判断，不用翻译层。

### 4.2 daemon ↔ MCP 的本地契约

- 传输：本地回环（回环 HTTP 或 Unix/Named Pipe），**不暴露到局域网**（云台是物理执行器，不是网络服务）
- 会话语义：daemon 串行处理命令（一次一条），并发提交返回 `busy`（沿用 antenna_sim「串行」纪律）
- 状态：`rotator_status` 读 daemon 缓存，不每次穿透到串口（避免状态查询抢占运动指令）

### 4.3 LoRa 链路（复用 dcp 帧）

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| magic / CRC | 0xD0CC / CRC-16-MODBUS | **不改** |
| type | `COMMAND 0x02` / `ACK 0x03` / `HEARTBEAT 0x04` + 新增云台类型 | 新增值需在 C 与 Python 两侧同步 |
| payload | `cmd_id(1) + az_i16(×10°) + el_i16(×10°) + flags(1)` | 定长，便于 ACK 对账 |
| 心跳 | 周期 ≤1s；超时 → 触发决策 3 的 failsafe | 超时阈值可配 |

## 七、实施结果与遗留

**已落地**（详见 `mcpserver/antenna_rotator/README.md`）：

- 主机侧 `mcpserver/antenna_rotator/`：protocol / safety / transport / daemon / lora / scan / tools
- 固件侧：`safety/safety_governor.hpp`、`net/serial_transport.hpp`、`net/lora_frame.hpp`、
  `net/lora_transport.hpp`、`runtime/rotator_runtime.hpp`，命令面新增 `M112/M115/$X/!/~/$FS=`
- 验证：**固件编译通过**（309389 B / 23% flash，21600 B RAM）；
  **主机规格测试 47 用例全过**；相关存量模块（antenna_sim / dcp）33 用例无回归

**实施中发现并解决的三个真问题**（都不是设计问题，是写下去才暴露的）：

1. **急停绕锁直写会破坏「一写一回显」的配对**——多出来的那条回显不补偿，
   之后所有命令都会拿到上一条的回复。修法：记「欠账」计数，下一次交换先排空。
2. **失联必须是设备侧行为**（见决策 3 的实现注记）——主机发不出命令。
3. **`#pragma once` 在 Windows 混合路径拼写下失效**——arduino-cli 把 `.ino` 的 include
   改写成绝对反斜杠路径，头文件之间的相对 include 是正斜杠，同一文件被两种拼写包含两次
   就报一屏 redefinition。修法：卷129/130 全部头文件补经典宏守卫（按名判等，不受拼写影响）。

**遗留（未做，明确登记）**：

1. **上机自检未跑**——无 ESP32 板与 SX1278。断言已写好，板子到位即可验证。
2. **LoRa 遥控端固件**——按决策 4 留给下一卷。
3. **B 方案混合轴**（方位步进 + 俯仰舵机）：`ServoOutput` 抽象已支持并存，但**方位 0..360°
   无法直接映射到 0..180° 舵机**——真机上方位轴必须走步进或加机械减速，
   这是运行时装配时才会暴露的约束，已记在 `rotator_runtime.hpp` 的注释里。
4. **限位开关（第四硬限位）**：当前只有软限位，纯软件保护。
5. **固件自校准命令未进命令面**：`ClosedLoopController::SelfCalibrate` 的最小二乘残差与
   「磁铁偏心」提示目前取不到，`rotator_calibrate` 只能报闭环遥测观测到的行程跨度（已在 note 标注）。
