## 二、最值钱的三处（附源码硬证据）

### 2.1 pyDEXPI 的 `GraphLoader` 与 `graph_memory` 只差一个适配函数

`pydexpi` 包的 `loaders` 下 `graph_loader.py` 第 25-52 行：

```python
class GraphLoader:
    """Loads a DEXPI model instance into a NetworkX MultiDiGraph."""
    def dexpi_to_graph(self, dexpi_model: DexpiModel) -> MultiDiGraph: ...
    def graph_to_dexpi(self, plant_graph: MultiDiGraph) -> DexpiModel:
        """Parsing the example graph back to pyDEXPI is not supported yet."""
        raise NotImplementedError
```

而 scratchpad 这侧 `graph_memory_adapter` 的 `engine.py` 第 189 行已经有批量入口：

```python
def ingest_entities(self, nodes: list[dict], edges: list[dict],
                    aliases: list[dict] | None = None, source_doc: str = "") -> dict:
    """nodes: [{"name","type","description"}]  edges: [{"source","predicate","target"}]"""
```

**中间只差 20 行转换**：`MultiDiGraph.nodes(data=True)` → `nodes`，`edges(data=True)` → `edges`（DEXPI 的边自带 `PipingNetworkSegment`/连接点语义，正好当 `predicate`）。这条打通的收益不是「多一个数据源」，而是**工厂图纸变成 agent 能走路的图**：问「这台泵断了，下游哪些换热器停」，走 3 跳就有答案。

反向缺口更值钱：`graph_to_dexpi` 上游是 `NotImplementedError`。KG 侧改了图（新增一条旁路、改一个阀门型号）**回写不成图纸**，闭环断在导出。这是可以自己补的小功能，也是能回贡上游的 PR 点。

### 2.2 HAZOP2RDF：风险本身是图，不是表格

`HAZOP2RDF` 做的是 **Excel ↔ RDF 双向**（README 原文：「transform the HAZOP data, which is stored in Excel format into RDF format and visa versa」），数据目录里直接放着真实 HAZOP 工作簿（`PEA-HAZOP-Dosiermodul_v07.xlsx` + 对应 `.ttl`）。

意义在于：**偏差（Deviation）—原因（Cause）—后果（Consequence）—防护（Safeguard）** 四元链条一旦进图，就能和 2.1 的 P&ID 图**叠在同一张图上**——设备节点同时挂着「工艺连接」和「失效后果」两类边。这才是 HAZOP 的真正形态：不是评审会记录，是设备图上的第二层标注。

对比：`peter023rs/hazop-ai` 走的正是这条路（P&ID 抽取 → 工厂 KG → AI HAZOP 推理），架构同构、10-14 还在推，**唯一问题是没 LICENSE**。下轮值得代发 issue，但按铁律得先给师傅过目草稿。

### 2.3 OPC UA 的 Information Model 与 SiLA2 是同一份 schema 的两种叫法

上一轮已经把 `openapi-to-sila2` 立为 Tier 1：SiLA2 的 `Command / Property / ObservableProperty` 对应 Hermes 的 `tool call / 只读 tool / 订阅流`。

这轮补上工厂侧：OPC UA 的 `NodeClass`（Object / Variable / Method）+ `TypeDefinition` + `Subscription` 是**同一组三件套**，只是多了「类型继承」这一层（SiLA2 没有）。所以设备描述可以一份出两版：实验室仪器走 SiLA2，工厂设备走 OPC UA，Hermes 侧只认一个 `device_descriptor`。

落地不是「装个 OPC UA 库」，是 mcpserver 下新建 `opcua_bridge` 目录，写三件事：
- `NodeId → tool name`（`ns=2;s=Pump1.Flow` → `pump1_flow`）
- `Method → tool call`（带 `InputArguments` 的类型签名）
- `Subscription → 流式 tool`（`DataChangeNotification` 推给 agent）

`opcua-asyncio`（LGPL-3.0）是纯 Python、有 `Subscription` 异步 API，适合包成 agent；`open62541`（MPL-2.0）当 C 侧参考和压力测试服务端。

## 五、与已有工作的关系（不重复的证明）

- **与轮 44（过程执行层）**：44 是运行期（能耗/分离/在线监控/SiLA2 仪器编排），45 是**图纸期与设计期**（P&ID / HAZOP / SIL）。交集仅「协议语义化」一处：44 的 SiLA2 是实验室仪器，45 的 OPC UA 是工厂设备，**共用一份 device_descriptor 而非同一实现**。
- **与轮 43（下游/酶/LCA）**：43 算「物质变成什么」，45 算「装置出事会怎样」，无重叠。
- **与 `iotgateway-协议边缘终结`（09-11）**：那份是 `DeviceAdapter` 设计稿（字段三元组 `偏移/缩放/单位`），45 的 `pymodbus` 是它的**下游实现库**，直接对接，不重写。
- **与 `spc` 判据（轮 44 `pyspc`）**：pyspc 判「漂移」（连续 7 点同侧等 8 条判据），ISA-18.2 判「报警洪水」（10 分钟报警数/抖动率/搁置率）。**一个管信号一个管操作员**，并列不替换。
