# Agent 治理与观测线规划 v1 — 从"跑得动"到"看得清、说得清"

> 沈遥 · 2026-10-09 · 依据：工单226/227 失败归因探针 + nanobot 对照（48903★ MIT）+ cpm 脉搏（13模块 1.91M 行，剩5天关键路径）

## 线的定位

scratchpad 已过"功能堆量"期（4783 py 文件）。下一程的瓶颈不是加功能，是**可观测性**——出了问题能不能定位（trace 诊断）、跑得好不好能不能量化（agent 观测）、做过的决策能不能审计（路由回填）。三份产能刚好凑齐这条线。

## 三件套

### 1. 轨迹诊断（已开工单227任务一）
- tools/trace_diagnose.py 冻结跳反事实探针——失败归因从"猜"到"测"
- 后续：接入真实 agent 轨迹（先从 hermes session db 的 tool_calls 流试起）

### 2. Agent 观测对标（P1，勘察级）
- **RagaAI Catalyst**（16k★ Apache-2.0）：agent 观测/监控/评估 SDK——trace 可视化与评估指标体系参考
- **nanobot**（48.9k★ MIT）：超轻量自托管 agent 框架——Lumo 同赛道对照。重点看它如何在"ultra-light"约束下组织记忆/工具/会话，对照我们的巨石拆分策略
- 产出：对照报告一份，判定哪些观测指标值得引进（token 成本/工具成功率/循环检测）

### 3. 评估闭环（P2）
- 把 cpm 脉搏（system_governance --pulse）从"架构体检"扩展到"行为体检"：每周自动跑一组标准任务，成功率/成本/延迟留痕入 InfluxDB（自部署波3）
- Grafana 出 agent 健康面板——与频谱面板并列，一屏看全

## 治理红线（借本次 v5.2.7/5.2.8 事故沉淀）
- 测试 patch 面完整性纳入 review checklist：凡 patch get_config 类配置函数，必须核对**装配链上每一层**的导入来源（病三教训）
- CI 干净环境视角验收：venv 无真 key/无缓存配置时测试必须绿（防"本机假绿"）
- 发版只顺延不删 tag；测试环境与 CI 环境差异显式记录在工单验收条款

## 钩子
- InfluxDB/Grafana（自部署波3）是本线的数据底座
- M3 digest 收口后，digest 质量抽检脚本可并入评估闭环（每批抽 20 篇人工核对）
