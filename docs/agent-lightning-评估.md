## 0. 结论速览

Agent Lightning 的核心贡献是把传统「单体 ReAct 循环」**解聚（disaggregate）**为可独立迭代的组件——规划、执行、工具、记忆各司其职——再用 **RL 后训练**直接在任务奖励上优化整个分解后的决策链。关键证据：仅 3.5K 行即可复现，SWE-bench 从 41.8% 拉到 56.4%（+14.6pp）。

对 NEKO 的自有 Agent 栈，最有价值的不是照搬框架，而是三条解聚原则 + 三个可复用组件（见 §3）。

## 1. 架构拆解

「解聚式」的本质是把一个隐式的 agent loop 显式化、模块化：

| 组件 | 职责 | 传统单体 vs 解聚 |
|---|---|---|
| Planner | 把任务分解为可执行的步骤/子目标 | 单体里是隐式的「下一步」 |
| Executor | 执行单个步骤（调工具、写代码） | 与规划耦合在同一上下文 |
| Tool/Env 层 | 标准化的工具调用与环境反馈接口 | 内嵌在循环里 |
| Memory | 跨步骤的状态与上下文管理 | 靠不断增长的对话历史 |

解聚后的收益：
1. **可独立训练/替换**：Planner 与 Executor 可分别用不同模型、分别 RL 微调。
2. **状态可审计**：每一步的输入/输出/奖励都是显式记录，便于 RL 信用分配。
3. **复现成本低**：接口清晰 → 3.5K 行即可复现，说明「解聚 + 显式接口」本身就能带来巨大的实现瘦身。

## 2. RL 后训练的价值

- 在任务成功/失败的**可验证奖励**上直接优化，而非只在 SFT 数据上模仿。
- 对 SWE-bench 类「结果可判定」的任务尤其有效——这与 NEKO 现有的「可验证奖励」方向（RLVR）完全同构。

## 3. 可借鉴组件设计（≥3）

### 组件 1：Planner-Executor 分离的「计划即数据」接口
- **设计**：Planner 输出结构化 `PlanStep[]`（每步含 `tool/action + 参数 + 依赖`），Executor 逐条消费。计划是可序列化的一等公民，可缓存、可重放、可 diff。
- **落点 NEKO**：把 NEKO 的 agent 循环改为「先出结构化计划 → 逐条执行」，计划落盘，为后续 RL 信用分配与故障归因提供锚点。

### 组件 2：RL 信用分配的「步骤级奖励记账」
- **设计**：每步执行后记录 `(step, action, outcome, reward)`，用结果驱动的信用分配（而非整轨迹平均）更新策略。
- **落点 NEKO**：复用现有 A26 信用账本的思想，把「Agent 间消息信用」扩展到「步骤级动作信用」，让低价值步骤被降级/剪枝。

### 组件 3：解聚式的轻量执行器池 + 统一工具接口
- **设计**：Executor 是无状态 worker（输入 step + 上下文 → 输出 result），可水平扩展；工具统一为 `name → (schema, callable)` 注册表。
- **落点 NEKO**：把工具调用从主循环里抽出成独立注册表（NEKO 已有插件注册机制，可对齐），执行器与规划器解耦后可单独量化/裁剪。

## 4. 评估结论

- **值得借鉴**：解聚式架构 + 步骤级 RL 信用分配，是 NEKO 多 Agent 协作从「能用」到「可训练、可审计」的清晰路径。
- **不建议照搬**：Agent Lightning 针对 SWE-bench 代码任务优化，其 Planner/Executor 粒度对 NEKO 的「无线电/Agent 协作」场景过细；应保留解聚思想、按 NEKO 任务重定义组件边界。
