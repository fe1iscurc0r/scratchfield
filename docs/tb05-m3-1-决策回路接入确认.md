## 一、结论（TL;DR）

**M3.1「投递到陆墨决策回路」是「部分完成」：apiserver 侧已完整接通，NEKO 侧发送端未接线。**

- ✅ **apiserver 接收 + 决策回路消费端已生效**：`/api/lumo/event` 端点 → EventBus v2 → `lumo_state`（状态快照）+ `lumo_proactive`（五门决策）两个消费者已在 `api_server.py` 启动时注册。
- ❌ **NEKO 侧发送端 `lumo_event_sender.py` 已实现但未接线**：`get_sender()` 在全仓库**无任何调用点**，事件实际上不会从 NEKO 发出，整条链路在源头是断的。
- ❌ **决策执行闭环未接通**：`lumo_proactive.on_user_input` 调用 `check()` 后**丢弃返回值**，决策出的「搭话文本」未回流到 `lumo_inject_router.py` 的 `/api/lumo/speak` 执行 TTS。

## 四、缺口清单

1. **【核心缺口】NEKO 侧发送端未接线**：`NEKO/N.E.K.O/main_logic/lumo_event_sender.py` 定义了完整的 `LumoEventSender`（6 类事件、队列、退避、鉴权、`get_sender()` 单例），但其 docstring 声称的「接入点以 import + 一行 emit 挂到 turn/tts 管线」**并未落地**——全仓库 grep 不到任何 `import lumo_event_sender` 或 `get_sender()` 调用，也找不到 `sender.user_input(...)` / `sender.tts_start(...)` 等 emit 调用点。事件源（turn/tts/asr 管线）与发射器之间没有任何连接。

2. **【执行闭环缺口】决策结果未回流 speak**：`lumo_proactive.on_user_input`（`lumo_proactive.py:138-149`）调用 `await self.check(...)` 后丢弃返回值；`_periodic_check`（`158-169`）同样丢弃。即「五门决策」只算出了要不要搭话、搭什么话，但该文本没有经 `lumo_inject_router.py` 的 `/api/lumo/speak` 发回 NEKO 执行 TTS（`lumo_proactive.py` docstring 也明确标注「speak 通道调用留待联调」）。

3. **【文档陈旧】`lumo_event.py` 模块 docstring 第 8 行**仍写「投递到 apiserver 内部事件总线（M3 阶段仅日志，决策回路接入留 M3.1）」——M3.1 消费端已接入，此注释与现状不符，需更新为「已接入 lumo_state / lumo_proactive」。
