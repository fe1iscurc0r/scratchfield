# 写操作确认门（卷121 W121-03 · 2026-09-17）

「先给计划/改动，用户点头才动手」。这一层挂在卷119 W119-03 的 `TOOL_PRE_EXECUTE` waterfall 上，
与审计门 / 敏感工具门 / 熔断门同一条洋葱链，不改 agentic loop 的执行路径。

## 三层结构

| 层 | 位置 | 作用 |
| --- | --- | --- |
| **PLAN 段** | 模型输出 `[PLAN]…[/PLAN]` | 纯展示：前端把标记渲染成「执行计划」卡片（`Markdown.vue::preprocessPlanBlocks`），loop 另发 `plan` 事件 |
| **确认门** | `apiserver/event_bus/confirm_gate.py` | 拦写操作、算真实 diff、管 pending / 放行 / 拒绝 |
| **落盘** | Code Workspace 工具自身 | 拿到放行后才写（dry_run 预览与实际写入是同一套 diff 逻辑） |

## 拦截流程

```
模型: file_write(path=a.py, content=…)
  └─ TOOL_PRE_EXECUTE waterfall
       ├─ 审计门（记 pre）
       ├─ 敏感门 / 熔断门（本工具在 allowlist，放行）
       └─ 确认门
            ├─ plan_confirm=false        → 放行（审计兜底）
            ├─ 签名在「一次性放行集」     → 消费并放行
            ├─ 签名在「拒绝集」           → veto「用户拒绝，请调整方案」
            └─ 其他                       → dry_run 预览真实 diff → 挂 pending
                                            → veto「等待用户确认：<diff>」
                                               + SSE `pending_confirm` 事件
用户: 「确认 / 继续 / 执行」（或前端按钮走 decide(sid,"confirm")）
  └─ 下一轮同签名调用命中一次性放行 → 真正落盘
用户: 「拒绝 / 取消 / 算了」
  └─ 同签名再次被 veto，文件 mtime 不变
```

签名 = `sha256(tool + 去掉下划线与 session_id 的入参)` 前 16 位。内容变了就是新一轮待确认，
不会拿旧确认放新改动。

## 关键词判定

`CONFIRM_KEYWORDS`：确认 / 继续 / 执行 / 同意 / 可以 / 好的 / 批准 / 允许 / 动手 / 就这样 / ok / yes / go ahead
`REJECT_KEYWORDS`：拒绝 / 取消 / 驳回 / 算了 / 不用了 / 不要改 / 别改 / 先别 / 停下 / 停止 / cancel / reject / no

**只在该会话确有 pending 时才判定**（否则「继续」这类日常词会被误吞），且拒绝词优先扫。
决策入口两个：对话关键词（`chat.py` 在进 loop 前调 `observe_user_message`，命中会回一个
`confirm_decision` 事件）、以及给前端按钮留的 `decide(session_id, decision)`。

## 状态与安全

- pending / 放行 / 拒绝全部**按会话隔离**，只存内存（进程内单例），不落盘内容明文
- 待确认项只保留 工具名 / 路径 / 签名 / diff，不存完整文件内容
- 每次 待确认 / 放行 / 拒绝 / 预览失败 都进审计（`audit/tool_calls.ndjson`，`phase=confirm_gate`）
- `code_space.plan_confirm=false` → 整门旁路，但工具仍登记在敏感工具清单里受审计口径覆盖

## 前端最小渲染

- `frontend/src/components/Markdown.vue`：`[PLAN]…[/PLAN]` → ```plan 围栏 → `<details class="plan-card">`
  （标题「📋 执行计划（写操作待确认）」，未闭合的流式输出也照常渲染）
- `frontend/src/components/MessageItem.vue`：`.plan-card` / `.plan-body` / `.plan-row` 样式
- 待确认的 diff 本身作为工具结果出现在消息里（走既有 `tool-result` 折叠块），用户据此点「确认」

## 配置

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `code_space.plan_confirm` | `true` | 写操作确认门总开关 |
| `bus.tool_gate.sensitive_tools` | 含 code_exec/file_write/file_edit/shell_exec/test_run | 登记进敏感清单（审计口径） |
| `bus.tool_gate.allowlist` | 同上 5 个 | 敏感门放行，真正的把关在确认门 + 沙箱 |

> 登记进敏感名单是为了让这些工具进入「敏感工具清单表」被审计口径覆盖；若不放进 allowlist，
> 敏感门会直接 veto（`audit_only=false` 时），功能不可用。二者必须同时改，README 这里写清楚。

## 实测证据

```bash
.venv/Scripts/python.exe tools/e2e_agentic_loop.py --confirm --max-steps 4 \
  --session e2e-w121-confirm \
  --prompt "用 code_workspace 在工作区写一个文件 hello.py，内容为 print('hello from confirm gate')；然后用 code_exec 跑它，最后告诉我输出。"
```

```
===== 阶段1 =====
[E2E] 第 1 次工具调用: ['code_workspace:file_write']
[E2E]   结果 file_write status=error: 等待用户确认：file_write → hello.py
         ```diff --- a/hello.py +++ b/hello.py @@ -0,0 +1 @@ +print('hello from confirm gate') ```
[E2E]   待确认写操作: ['hello.py']
[E2E] 待确认: file_write → hello.py (sig=3821c9e33bf038b7)
[E2E] 用户回复「确认，执行」→ 确认门决策=confirm
===== 阶段2（确认后） =====
[E2E] 第 1 次工具调用: ['code_workspace:file_write']
[E2E]   结果 file_write status=success: {'ok': True, 'created': True, 'dry_run': False, …}
[E2E] 第 2 次工具调用: ['code_workspace:code_exec']
[E2E]   结果 code_exec: {'stdout': 'hello from confirm gate\n', 'exit_code': 0}
===== 工作区 …/workspace/e2e-w121-confirm =====
- hello.py (32B)
```

阶段 1 结束后工作区为空（未落盘），阶段 2 才出现 `hello.py` —— 确认门确实卡在写入之前。
