# 态势感知系统 · 工单缺陷与偏离说明（卷 132 / 第 43 期）

> 编写：执行方（deepseek→k3 接力，前端 F-01~F-08 + 收口后端 B-02/B-07/B-08）
> 日期：2026-09-18
> 对应工单：`TRAE_WORKORDER_PROMPT_AGENT_132.md`、前端工单 `态势感知系统-前端工单-Kimi-2026-09-18.md`

本文件记录在**严格按工单落地**时发现、核实并修正的缺陷与偏离。结论先行：**工单正文
存在多处会直接阻断运行的错误**，若照抄会 404 / 导入冲突 / 静默丢数据；以下是逐条处理。

---

## 1. 顶层包名 `gevent/` 与依赖 `gevent` 同名冲突（最严重）

工单把后端目录命名为 `gevent/`，同时又把它列为 pip 依赖（`greenlet` 协程库）。
二者同名会让 `import gevent` 在「包优先」时遮蔽真正的依赖，是自造的导入炸弹。
**处理**：整个目录改名 `sitaware/`，`__init__.py` 顶部注明原因。该依赖在本架构中根本
不需要（FastAPI + httpx 已覆盖异步 HTTP）。

## 2. `gcoord` 是 JS 库，PyPI 404

工单的 `requirements` 里写 `gcoord`。它是 JavaScript 坐标系转换库，**PyPI 无同名包**
（实测 404）。**处理**：删除该依赖，自研 `sitaware/coords.py` 实现 WGS84 / GCJ-02 /
BD-09 互转（迭代逆变换）+ Maidenhead 网格互转，经探针验证（6 位格子 8.5×4.6 km、
10 位 85×46 m）。

## 3. `gevent[fastly]` extra 不存在

工单 requirements 出现 `gevent[fastly]`。该 extra 不存在。**处理**：不使用 `gevent`，
自然无此 extra。

## 4. `radio_brain/articles.jsonl` 不存在（工单声称「已有」为假）

工单 B-02 暗示该语料已存在可直接用。**处理**：核实目标仓无此文件。B-02 改为
「注入式采集」——`DemoCollector` + `EventPipeline`（采集→规范化→去重→落库），真实源
（news/ham/weather/user）通过 `Collector` 子类扩展，不依赖不存在的假资产。

## 5. `pysqlite3-binary` 无 Windows 轮子

工单指定 `pysqlite3-binary`。其实测只有 `manylinux2014_x86_64` 轮子，**Windows 装了也
起不来**（本机是 Windows）。**处理**：改用标准库 `sqlite3`（零依赖、跨平台）。缓存层
`CacheStore` 用「整行存完整 payload JSON」实现无损存储，加字段不会因漏 `ALTER TABLE`
而静默丢数据。

## 6. 后端 B-07 漏列两个前端依赖端点

前端 F-04 需要告警规则 CRUD，F-05 需要自然语言查询，但工单 B-07 的接口表里**没有**
`/api/alerts` 与 `/api/situation/query`。**处理**：后端补齐 `AlertRule` 模型 +
`AlertStore`（SQLite 持久化）+ `SituationEngine.answer_query`，暴露这两个端点。这是
「接口契约交叉比对、缺口以双方清单并集为准」的体现。

## 7. `coord_source` 取值错误：`gcoord|wgs84|bd09`

工单数据模型把 `coord_source` 写成 `gcoord|wgs84|bd09`，其中 `gcoord` 是**库名**而非
坐标系。**处理**：改为 `gcj02|wgs84|bd09`（见 `models.CoordSource`）。内部统一 WGS84，
`coord_source` 只记录入站声明用于审计。

## 8. `GET /api/situation/summary` 与 `POST` 自相矛盾；`WS` 名实不符

- 工单一处写 `GET /situation/summary`，另一处写 `POST`。统一为 **POST**（带 body 的
  聚合查询，GET 不合理）。
- 工单多处写「SSE 实时推送」却又标 `WS /ws/events`。WebSocket 与 SSE 是两套协议。
  **处理**：统一为 **SSE（`text/event-stream`）**，端点 `/api/events/stream`，用
  `sse-starlette` 实现。前端用原生 `EventSource` 订阅。

## 9. Maidenhead 6 位「误差 <100m」几何上不可能

工单称 6 位 Maidenhead「定位误差 <100m」。**实测**：6 位格子约 8.5km×4.6km（对角线近
10km），绝不可能 <100m。10 位才约 85m×46m。**处理**：判据改为「误差 ≤ 半格对角线 +
精度单调收敛」，仅对 10 位及以上做高精度断言；`coords.maidenhead_cell_size_m` 返回真实
尺寸以免误判。

## 10. APRS 复用目标 `mcpserver/rf_brain/aprs_igate.py` 在本 checkout 不存在

工单 B-08 要求复用既有 `aprs_igate.py`（Maidenhead 转换 / APRS-IS 登录 / GeoJSON 导出 /
去重）。**核实**：本 checkout 无此文件。**处理**：`sitaware/ham_processor.py` 改为
自包含实现——Maidenhead 转换复用本包 `coords`，APRS/ADIF 用轻量解析，并保留演示站点
保证 `/api/ham/stations` 非空；docstring 注明若有 `aprs_igate.py` 可在 `load_stations()`
优先调用其 `to_geojson_features()`。

## 11. 前端框架偏离：Nuxt 4 → Vite + Vue 3 + TS

工单推荐 Nuxt 4（或 React + Next 15）。**处理**：独立建 `sitaware-ui/`，技术栈
Vite + Vue 3 + TypeScript + Pinia + vue-i18n，**不混入根 `frontend/`**（那是 NEKO
Electron 主应用，与本系统无关）。理由：避免 SSR 与 Electron 主应用的构建耦合，独立
`npm run dev` / `npm run build` 即可联调；地图组件在客户端初始化，无 SSR 注入问题。
