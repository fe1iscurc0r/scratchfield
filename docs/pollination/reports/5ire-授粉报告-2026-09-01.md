## 2. 核心数据结构共鸣（最值钱 3 处）

1. **ContentBlockConverter 的统一内容块模型**（`src/intellichat/mcp/ContentBlockConverter.ts:12-59`）
   `FinalTextBlock / FinalAudioBlock / FinalImageBlock` 三态联合 + `origin`（document/resource_link）溯源。MCP SDK 的 ContentBlock 是"协议中立"的，各家 LLM 的 message content 是"厂商私有"的——这个转换器就是两者之间的唯一契约。**为什么值钱**：NEKO 要接多模态（IC-705 语音、SDR 频谱图、材料显微镜图），现在每条通路各写各的转换，5ire 给了统一的"协议块 → 厂商块"映射范式，直接套。

2. **MCP 五件套生命周期管理**（`src/main/services/mcp-servers-manager.ts:17-69`）
   `Stateful.Persistable` + memoize 的 liveServers/liveActiveServers 双缓存 + shortId 映射。**为什么值钱**：MCP server 有状态（激活/停用/连接中），scratchpad 的 mcpserver 目录现在只管"启动"不管"状态机"，5ire 的 manager 模式（状态持久化 + 实时查询 + 短路缓存）是完整的参考实现。

3. **BaseReader 流式解析抽象**（`src/intellichat/readers/BaseReader.ts:17-50`）
   构造注入 `ReadableStreamDefaultReader`，子类只覆盖 `parseTools/parseToolArgs`。**为什么值钱**：多 provider 的流式差异集中在"怎么解析 tool_calls"，5ire 把"解码 → 聚合 → 工具提取"固化成模板方法。云端 tokenrhythm 流式 brotli 偶发坏的问题，正好需要这种"解码层独立、解析层可替换"的架构。
