# 冻结跳反事实探针 → Agent 轨迹诊断器设计稿（工单226 任务三）

> 日期：2026-10-09 ｜ 料源：arXiv 2608.20627（AgenticRAG-FP，digest 在案）。
> 对口：多跳工具调用轨迹的失败归因——"哪一跳才是病根"。

## 1. 冻结跳反事实探针机制拆解（论文核心）

传统诊断是"覆盖式"（re-run 整条轨迹看哪儿输出变了）——深度 >1 时输出几乎处处变，
归因为 0.00。论文的干预式方法：

```
原轨迹 T = [h1 → h2 → h3 → h4 → out]   （多跳，某跳有病）

冻结跳探针 frozen-hop counterfactual：
  选定跳 k（如 h2）
  ├─ 冻结：把 h2 的中间结果固定为"参考值"（人工标注的正确值 / 另一条成功轨迹的同位值）
  ├─ 重放：h3、h4 以冻结后的 h2 为输入重新执行（LLM/工具真跑，不是回放记录）
  └─ 判据：out' = out ？ out' ≠ out ？
       out' 变好了 → h2 是因果跳（病根在 h2 或其前）
       out' 不变   → h2 非因果（病根在后段）
```

论文结果：深度 2 上归因准确率 **0.67 vs 覆盖式 0.00**。要点：**冻结产生的是受控反事实**
（只改变一跳，其余真跑），而不是"整条重放"（处处变，无法归因）。

## 2. scratchpad 落点：轨迹诊断工具设计

**位置**：`tools/trace_diagnose.py`（诊断工具，不进运行时热路径）+ 后续视需求挂 mcpserver。

```
输入:  一次失败的轨迹记录（含每跳的输入/输出/tool 名）
       + 参考轨迹（成功的同任务轨迹，或人工提供的正确中间值）
处理:  for k in range(1, len(hops)):
           frozen = 参考轨迹的 hop_k 输出
           out_k  = 重放(hops[k+1:], 前缀=hops[:k-1] + frozen)
           delta_k = diff(out_k, 原out)
输出:  因果跳序（按 delta 排序）+ 每跳的 diff 摘要 + 置信标注
       （单参考轨迹 = 单样本归因，标注"需 ≥2 参考交叉验证"）
```

**关键实现约束**：
- 重放需要**工具调用的确定性**——LLM 跳重放要固定 temperature=0 + 固定 prompt；
  非确定跳的 delta 只做参考（设计里显式标注，不冒充因果结论）；
- 中间结果快照必须完整（见 §3 对接点）——缺快照的跳无法冻结，只能跳过并记录。

## 3. 与现有 trace/span 体系的对接点

- **数据源**：apiserver/event_bus 的 trace/span（W119 体系）——工具调用轨迹已在
  tool_calls.ndjson + bus events 落档；诊断器读这两处拼轨迹；
- **缺口**：现有 span 记录的是"调用与结果"，**没有"中间表示标准化"**（冻结需要可注入的
  hop 输出格式）——PoC 阶段用"工具输出 JSON 原样回填"（大多数工具跳天然满足）；
- **执行器**：重放走 `mcpserver/workflow/chains.py`（工单189-C 的声明式链）——
  链的步骤天然可从任意前缀续跑（失败短路设计的反向利用）。

## 4. 最小 PoC 范围（不跑全 benchmark）

1. **输入**：trace 档里的 1 条真实失败链（或合成 3 跳链：检索→计算→写报告，注入已知错）；
2. **实现**：冻结 = 链的 step 输出替换；重放 = chains.py 从该 step 后续跑；
3. **判据**：合成链注入点已知 → 验证诊断器输出与注入点一致（3 案例）；
4. **不做**：benchmark 级评估、LLM 跳的非确定性建模、多参考轨迹仲裁。
预计 ≈1 天。

## 边界

- 论文 0.67 是深度 2 的数字；更深轨迹的归因力论文未给强结论——工具输出的置信标注要如实；
- 重放会**真实调用工具/LLM**（有成本）——设计上必须带"干跑预览"（先列将执行的跳再确认）。
