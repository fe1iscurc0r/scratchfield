## 1. FAOPs：把工单抽象成四元组

### 1.1 模板

```
工单（Workorder）
  ├── 步骤（Step）      有唯一 id、前置条件、动作、产出物
  ├── 证据（Evidence）  每个步骤的验收命令 + 实际返回（可复跑）
  └── 状态（Status）    pending / in_progress / done / blocked(原因)
```

四元组约束：
1. **步骤必须有可执行动作**（命令或文件落点），禁止"分析一下"这种不可判定项；
2. **证据必须是命令 + 返回**，不接受"已确认"；
3. **状态迁移必须留痕**（谁、何时、依据哪条证据）。

### 1.2 逐字段示例（拿本单 264 当样本）

| 字段 | 本单实例 |
|---|---|
| 工单 id | `WO-264`（指令文件 `TRAE_WORKORDER_PROMPT_AGENT_264.md`） |
| 步骤 A | 动作：写 `docs/pollination/2026-10-17-授粉点-射频链.md`；前置：`docs/pollination/` 已存在；产出：≥80 行含四段 |
| 证据 A | `wc -l` 返回行数 + 四段小标题 `grep` 命中 |
| 步骤 D | 动作：写 `docs/operate/fetch-arxiv-baseid-bugfix-2026-10-20.md`；前置：`docs/operate/` 需新建；产出：diff 段 + 副作用段 |
| 证据 D | `grep -c "VERSION"` = 1 |
| 状态 | A/B/C/D/E 各自 done 或 blocked(原因) |

**注意**：本单不新建 `docs/workorders/INDEX-active.md`（WO-243 尚未落地），模板只在此文档内示范。

## 2. TEM：版本化事实

### 2.1 最小表结构

| 列 | 类型 | 说明 |
|---|---|---|
| `fact_id` | TEXT | 事实稳定标识（同一事实的所有版本共用） |
| `value` | TEXT | 该版本的值 |
| `source` | TEXT | 来源（工单号 / 文档路径 / 测量命令） |
| `valid_from` | TEXT | 生效时间（ISO8601） |
| `valid_to` | TEXT | 失效时间；`NULL` = 仍有效 |
| `superseded_by` | TEXT | 被哪条新记录取代（自引用 `fact_id` + 版本） |

### 2.2 DDL

```sql
CREATE TABLE IF NOT EXISTS facts_versioned (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  fact_id       TEXT NOT NULL,
  value         TEXT NOT NULL,
  source        TEXT NOT NULL,
  valid_from    TEXT NOT NULL,
  valid_to      TEXT,
  superseded_by TEXT,
  UNIQUE (fact_id, valid_from)
);
CREATE INDEX IF NOT EXISTS idx_facts_current ON facts_versioned(fact_id) WHERE valid_to IS NULL;
```

**要点**：`valid_to IS NULL` 的那一行就是"当前值"；查询历史用 `WHERE fact_id=? ORDER BY valid_from`。
**不许 UPDATE 覆盖**——只 INSERT 新版本 + 给旧版本补 `valid_to`。

### 2.3 为什么这对我们有用

我们的工单偏差记录（如"工单写的路径不存在"）现在散落在 PR 描述里，属于**只写一次的事实**。
按 TEM 版本化后，"某路径在 10-19 是这个、10-20 变成那个"可查询，不用翻 PR。

## 3. MCP 能力洗白扫描（8 个检查点）

> 只写**检测维度**，不写利用步骤。依据 `cs.CR 2610.22301` 的"看实际能力而非声明"。

| # | 检查点 | 判定方式 |
|---|---|---|
| 1 | **声明 vs 实际工具数** | `tools/list` 实际返回数 vs 插件清单里声明的数量，不一致即标记 |
| 2 | **description 与实际参数** | 参数 schema 里是否有未在描述中提及的字段（尤其 `path`/`url`/`exec`） |
| 3 | **文件系统可达范围** | 是否接受绝对路径、是否限制在指定工作目录 |
| 4 | **网络出站能力** | 是否可发起任意 URL 请求（含内网地址/CIDR） |
| 5 | **进程执行能力** | 是否暴露 `exec`/`shell` 类参数，即使名字不同（`cmd`/`run`/`invoke`） |
| 6 | **凭据接触面** | 是否读取环境变量里的 token/密钥；是否把凭据写进日志 |
| 7 | **副作用可逆性** | 写操作是否可撤销（有 delete/overwrite 而无 backup 即标记） |
| 8 | **来源与更新** | 插件版本与来源仓库是否可追溯到具体 commit |

补充 2 条（共 10 条，任选 8 条以上落地）：
9. **跨工具串联风险**：A 工具产出的路径能否直接喂给 B 工具（组合后才越权）。
10. **静默降级**：失败时是否返回"成功"（把错误吞掉最危险）。
