## 二、六个闸门变量（都是**仓库变量**，零代码）

| 变量 | 控制什么 | 现状（2026-10-17 20:59） | 打开后的影响 | 建议 |
|---|---|---|---|---|
| `ENABLE_LINT` | `ci.yml` 的 **lint** job（ruff + frontend `npm run lint` + 本仓静态守卫） | **未设** | 每次 push/PR 到 main 都会跑；ruff/前端存量问题会让 PR 变红 | ✅ 可开（先在 PR 上验一次基线，见 §四） |

## 三、回滚（必须先读再动手）

**症状 → 处置**：

| 症状 | 含义 | 动作 |
|---|---|---|
| job `conclusion=failure` 且 `runner_name` 为空、`steps=[]`、annotation 含 "not started because recent account payments" | 计费再次被拦 | **立刻删掉对应变量**（`DELETE /actions/variables/{name}`），恢复"跳过"状态，避免永久红灯 |
| job 正常跑但红 | **代码/存量问题**（正常现象） | **不要删变量**；按 §四 建基线、分批修 |
| 变量设了但 run 显示 `skipped` | 变量名拼错或作用域不对（环境变量 vs 仓库变量） | 核对拼写；job 级 `if` **不能引用 `env` context**（历史坑，见 `ci.yml` 注释） |

> 铁律沿用：**闸门关闭的初衷是"别让红灯变狼来了"**。开闸后第一轮若大面积红，先修基线而不是再关闸。

## 四、开闸后的第一件事：建基线（不要直接盯 PR 绿）

1. **在 PR 上验**（爆炸半径最小）：把带 CI 改动的分支推上去，让 `pull_request` 事件触发 lint/smoke，拿到真实结论；
2. **记录三项基线**：`ruff check .` 的 error 数、`npm run lint` 的 error 数、`pytest -m smoke` 的 passed/failed；
3. **按"存量问题单独立单"处理**：不要混进功能 PR（否则功能 PR 永远红，又回到狼来了）；
4. 基线绿了之后，才考虑给 main 加 branch protection（要求 CI 通过）。

## 五、已就位的**本地**守卫（不依赖 CI，当下即生效）

| 守卫 | 落点 | 触发 | 覆盖 |
|---|---|---|---|
| 静态硬线脚本 | `scripts/verify-runtime-env-wiring.py --ci` | 手动 / pre-commit / **CI lint job 第一步** | 包内 runtime 接入、本机硬编码清零、NEKO 失败可诊断、开发模式不被注入污染、build 文件未被误改 |

> 三者与 CI 的关系：CI 正常时它是第一道；CI 被拦时（本地/计费）后两者仍生效 —— **不把验证绑死在 CI 可用性上**。
