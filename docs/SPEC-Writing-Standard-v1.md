# SPEC 写作规范 · v1（spec 的 spec）

> 用途：统一所有 SPEC 的写作标准，供 WorkBuddy（Kimi K3）/ Trae / Hermes 写 SPEC 与审 SPEC 时执行。
> 读者：AI 施工方（**不共享写作者的上下文**，SPEC 必须自包含）。
> 一句话：**SPEC 是「施工图」，不是「计划」，也不是「工单」。**

---

## 一、三层文档分离（先分清要写哪个）

| 文档 | 给谁 | 回答什么 | 命名 |
|------|------|---------|------|
| **计划 (Plan)** | 人 | 为什么做、做什么、优先级 | `*-Action-Plan-*.md` / `*-Master-Plan-*.md` |
| **SPEC** | AI 施工方 | 怎么做、接口定义、测试用例、验收 | `*-SPEC-v<N>.md` |
| **工单 (Work Order)** | AI 施工方 | 现在做哪个、多久、推到哪 | `*-Batch-Work-Order-*.md` |

**一份文档只做一件事。** 别把"为什么做"的长篇论证写进 SPEC，别把施工细节塞进计划。

---

## 二、SPEC 必含章节（缺一不可，顺序固定）

1. **〇、一句话定位** —— 一句话说清这个 SPEC 干什么、边界在哪
2. **一、背景与边界** —— 现状（引用相关文档/文件）+「做什么 / 不做什么」对照表
3. **二、架构设计** —— 数据流图 + 组件清单表（文件 | 类型[新建/修改] | 说明）
4. **三、施工步骤** —— 每步带：目标文件 + 具体代码骨架 + 改动量（"约 5 行"）
5. **四、关键假设与 fallback** —— 每个不确定点：假设是什么、验证方法、不符时怎么兜底
6. **五、已知限制** —— 诚实标注：什么做不了、为什么（见第四节红线）
7. **六、测试用例** —— 可直接跑（见第六节要求）
8. **七、交付物清单** —— checkbox 格式，可逐项核对
9. **八、验收标准** —— 可量化（见第五节要求）
10. **九、提交规范** —— commit message 格式 + 分几次提交

> 可选：**附、与下一步的衔接** —— 本 SPEC 落地后，后续 SPEC 能否复用其产出。

---

## 三、质量红线（硬性，每条可 grep/肉眼检查）

1. **代码骨架必须可直接用** —— 施工方不共享上下文，SPEC 里出现的代码片段要能直接粘贴运行，不能是"伪代码示意"。
2. **引用必须到文件 + 行号** —— 说"改 `lumo_event.py` 第 4 步"要给出实际位置（如 `lumo_event.py:207`），不能只说"某处"。
3. **不预设"试试看"** —— 做不了的写「不能做 + 原因」，不写「可以试试」。迂回路径要显式标「迂回」。
4. **每个 LLM 调用点必须显式声明** —— 有无 LLM、在哪调、token 开销，写进架构或步骤。避免隐藏的 token 黑洞。
5. **边界用表，不用散文** —— 「做 / 不做」「假设 / fallback」用表格，别用大段文字。

---

## 四、已知限制写法（诚实标注，防假验收）

坏写法（❌）：`"降级逻辑后续完善"` —— 含糊，等于没写。
好写法（✅）：`"降级只标记不切换：error 事件打标记但不实际切纯文本——那需要改 NEKO 侧配置，超出本 SPEC。"`

**每条限制必须含：具体是什么 + 为什么不做/超出范围。**

---

## 五、验收标准写法（可量化，grep/assert 级别）

坏写法（❌）：`"跑通"`、`"功能正常"`、`"无明显 bug"`。
好写法（✅）：

```
1. 三个测试用例 `python -c` 输出 PASS 1/2/3
2. `grep -n "lumo_state" apiserver/routes/lumo_event.py` 返回非空（已接线）
3. 原有逻辑未被改动：`git diff` 确认仅第 4 步追加
4. 无新增 LLM 调用：`grep -n "acompletion" lumo_state.py` 返回空
```

**规则：每一条验收标准必须能被一条命令或一个 assert 验证。**

---

## 六、测试用例要求（必须能跑，纯 Python 优先）

1. **纯 Python 模块 → 云服直接跑**：`python -c` 或 `pytest` 能过 = 逻辑正确，真机只是部署环境。别把测试写成"需要手动点 UI"。
2. 需要 NEKO 真机 / 浏览器 / 硬件的测试，**单独列为「端到端验证」**，与可自动化的单元断言分开，明确标注"需真机"。
3. 每个测试用例带预期输出（`assert` 或 `print("PASS N: ...")`）。

---

## 七、命名 + 版本规范

- 文件名：`<主题>-SPEC-v<N>.md`，主题用英文小写连字符（避免编码问题），版本从 v1 起。
- 修订：小改在正文末尾追加「修订记录」，大改升版本号（v1 → v2）。
- 放置：`docs/` 目录（与计划、工单同目录，施工方按文件名引用）。

---

## 八、反模式（坏 SPEC 长什么样）

| 反模式 | 症状 | 后果 |
|--------|------|------|
| 计划当 SPEC | 大段"为什么做"的论证 | 施工方找不到怎么做 |
| 无代码骨架 | 只有文字描述 | 施工方瞎猜，产出跑偏 |
| 验收不可量化 | "跑通即可" | 无法判断做完没 |
| 隐藏 LLM 调用 | 步骤里不提 token 开销 | 施工完才发现 token 黑洞 |
| 假设不写 fallback | "session_id 应该一致" | 验证不符时施工方卡死 |
| 测试要真机 | 全部测试要手动点 UI | 云服无法验收，阻塞交付 |

---

## 附：本规范的验证方式

审 SPEC 时，逐条问：
1. 十个章节齐了吗？
2. 每条验收标准能 `grep`/`assert` 验证吗？
3. 每条已知限制有"具体 + 原因"吗？
4. 测试用例云服能跑吗？
5. 代码骨架能直接粘贴运行吗？

五条全过 = 合格 SPEC。缺一条 = 打回补。
