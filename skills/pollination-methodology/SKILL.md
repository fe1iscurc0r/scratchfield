# 授粉方法论 (Pollination Methodology)

> 授粉不是 fork 粘贴，是"拆解 → 改造 → 集成 → 留下报告"。
> 每个外部灵感都登记：来源、许可、改造点、验收——法律与道义都讲得清。

## 核心原则（不可妥协的四条）

1. **不套壳** — 引入的组件必须消化：至少理解其架构、能说清"我们改了什么、为什么"。原样挂 logo 转卖 = 偷。
2. **账本先行** — 每次授粉前先查许可证并登记（FUSION-LOG / NOTICE），许可不明不引入。兼容性底线：入站许可必须与主仓兼容（如 MIT/Apache/BSD → AGPL 单向兼容）。
3. **参考级 vs 移植级** — 不是所有值得学的东西都该抄代码：
   - **移植级**：许可干净、依赖轻、直接可用 → 拆出需要的部分集成
   - **参考级**：太老/依赖太重/许可不适配 → 只抄设计思想，独立重写，账本记"机制参照，零拷贝"
4. **验收闭环** — 移植完必须能跑、能测、能说清差距。失败品不扔：降级进慢通道继续生长。

## 双通道流水线（漏斗 + 树）

### 入口评分（每颗种子打三分）
| 维度 | 问题 |
|------|------|
| 价值密度 | 能否直接指导行动/直接移植？ |
| 时间敏感 | 错过是否损失窗口？ |
| 条件成熟 | 硬件/资料/时机现在齐不齐？ |

**高价值 + 高敏感 + 条件齐 → 漏斗；高价值 + 慢成熟/条件不齐 → 树。**

### 漏斗（快通道，小时~天）
1. **粗筛**：来源白名单 + 关键词 + 新鲜度，拦掉 80% 噪音
2. **评分**：价值密度算分，低于阈值转树（不丢）
3. **验证**：试跑 / 真机 / 交叉验证，通过则落库（patch/文档/配置）
4. 失败的产物是树的肥料——用不了但有意思的部分顺手种进树

### 树（慢通道，周~月）
状态机：`Seed → Rooted → Sprout → Branching → Bloom → Fruit`

| 状态 | 含义 |
|------|------|
| Seed | 原文 + 摘要 + 为什么值得种（判据是"意义"不是"速度"） |
| Rooted | 吸收关联资料 |
| Sprout | 形成初步理解 |
| Branching | 跨域连接（同主题种子聚成分支） |
| Bloom | 落地条件成熟 |
| Fruit | 产出成果 → 升级回漏斗执行 |

推进引擎双轮：
- **被动**：定时任务定期检查状态机（一次搭好，增量自动跑）
- **主动**：处理 A 时发现关联种子 B，B 的状态当场推进

### 通道间转化
- 漏斗失败品 → 降级进树
- 树成熟品 → 升级回漏斗
- 两通道共用同一知识底座（索引/SQLite）
- 漏斗快不是孤立快，是树在底下撑着——树攒的跨域连接提高漏斗的判断速度

## 报告规范

每次授粉产出一份报告，模板：

```markdown
# <来源项目> 授粉报告 <日期>
## 来源（owner/repo、Stars、许可、验证方式）
## 它有什么（核心机制拆解）
## 我们缺什么（差距清单，标 P0/P1）
## 移植方案（移植级/参考级 + 改造点）
## 验收（怎么证明移植成功）
```

## Pitfalls（血泪换的）

> 本节持续增补——每踩一个新坑就多一条，方法论和作物一样是活的。

- **克隆前先确认真实 owner/repo**：API 返回的 repo 名 ≠ 路径（例：`code-review-graph` 实际是 `tirth8205/code-review-graph`）
- **测试文件不放在被测包目录下**：会触发循环导入；放 `tools/test_*.py`，`sys.path.insert` 导入被测模块
- **新任务先读现有代码再设计**：已实现的模块往往有完整基础，先找 Gap 不要从头造
- **许可字段不可全信**：API 的 license 字段在 LICENSE 文件缺失时不可信，以仓库实际文件为准
- **重依赖项目只抄架构**：例：Python2 时代项目只抄链式编排思想，不移植代码
- **报告必须含差距清单**：没有 P0 优先级的报告，后续实现没有抓手
- **失败品先降级再丢弃**：验证不过的种子进树慢养，常常几个月后在别的分支上开花
