## 1. 修复点清单

### HIGH-1：Protocol isinstance 短路 validate_adapter → CAPABILITY 7 字段 / 三线对齐门禁整体失效

**原代码**（`adapters/__init__.py:62`）：
```python
if not isinstance(mod, MCPAdapterModule):
    issues = validate_adapter(mod, name)
    if issues: continue
```

**根因**：`isinstance(mod, Protocol)` 只做 hasattr 三要素（CAPABILITY/healthcheck/register），只要属性存在就 True，直接跳过 `validate_adapter` 的字段级深度校验。导致 CAPABILITY 里写空字符串 `vendor=""`、`name` 与注册名错位、`_from_adapter` 写错模块名 —— **全不拦截**。

**修复**（2 个文件）：
- `_common.py:L174`：`_REQUIRED_CAPABILITY_KEYS` 从 6 字段**扩展为 7 字段**（`name/displayName/description/version/license/vendor` → 新增 `_from_adapter`）
- `_common.py:L227-L235`：`validate_adapter` 增加**三线对齐**校验第 2 条：
  `CAPABILITY._from_adapter == registered_name`（第 1 条原已有 `CAPABILITY.name == registered_name`）
- `__init__.py:L61-L88`：**去掉 isinstance 短路**，无论 isinstance 结果如何都强制跑 validate_adapter；isinstance 失败但 validate_adapter 没 issue 时，再加兜底 "不满足 Protocol" 提示

**影响消除**：现在 `isinstance(mod, MCPAdapterModule) == True` 但 `vendor=""` / `_from_adapter="vulnclaw"` 写在 `memclaw` adapter → validate_adapter 一定会识别并阻断，不再 "假性通过"。

### MEDIUM-4：`_ADAPTER_CAPABILITY_NAMES` 读写分离，adapter 忘调 safe 时冲突检测失效

**原代码**：`__init__.py` 步骤 4 只**读** `_ADAPTER_CAPABILITY_NAMES`，写入只在 `register_capability_safe` 内部（_common.py:L164）。维护者在 register() 里忘了调 safe → 步骤 4 过了 → healthcheck/register 全执行成功，但 _NAMES 表**未写 entry** → 下一个同名 adapter 再进来步骤 4 读空表 → 冲突检测完全漏报，两个 adapter 一起跑，后一个能力卡片被前者**静默覆盖错位**。

**修复**（`__init__.py:L75-L88`）：步骤 4 门禁通过即**立即写入** `_ADAPTER_CAPABILITY_NAMES[cap_name] = cap_from`，不再依赖 register() 自觉。与 safe 不冲突：safe 内部 prev 检测时 `prev == who` 判定为同模块重入，不打重复 WARNING。

### HIGH-2：manifest / mcporter / adapter 三条写入路径互不跨源查重，同名能力错位

**原代码**（3 条写入路径）：
- `scan_and_register_mcp_agents()`：写 MCP_REGISTRY + MANIFEST_CACHE，**不反查** `_ADAPTER_CAPABILITIES`
- `register_external_mcp_agents()`：查重范围仅限 MANIFEST_CACHE / MCP_REGISTRY，**不碰 adapter 域**
- `register_capability()`：只查 `_ADAPTER_CAPABILITIES` 内部，**不反查 MANIFEST_CACHE**

**触发场景**：本地加一个 `mcpserver/headroom/agent-manifest.json` `{"name":"headroom"}` → list_registered_capabilities 同时出现两条（manifest+adapter）；`get_service_instance("headroom")` 只取 manifest 那份，但工具实际挂在 adapter 名字空间。**能力卡片可见但工具调用错位**，排障至少要追 3 个文件。

**修复**（仅改 `mcp_registry.py`，不重构三张表）：
1. **新增纯函数** `_check_cross_source_conflict(name, new_source)` 统一做并集查重：跨 MANIFEST_CACHE（manifest / mcporter 两域）+ `_ADAPTER_CAPABILITIES`（adapter 域），不同源 → 打 WARNING（**不阻断**，避免 mcporter 新配置被老 adapter 锁死登记不了）
2. **三处写入路径前置调用**：scan_and_register(`"manifest"`) / register_external(`"mcporter"`) / register_capability(`"adapter"`)
3. **list_registered_capabilities 末尾**：同名跨源条目自动附带 `conflict_sources: ["manifest", "adapter"]` 字段告知用户有重名；单源条目不附该字段（减少噪音）
4. **mcporter source 细分**：`MANIFEST_CACHE[name]["source"]=="mcporter"` vs 本地 scan 走默认 `"manifest"`，在 conflict_sources 里精细区分

### MEDIUM-3：`inject_vendor_path` 无 vendor/top5 边界校验，架构级路径逃逸缺口（补本轮）

**原代码**：
```python
def inject_vendor_path(name: str, *subpaths: str) -> None:
    ...
    for sub in reversed(subpaths):
        p = str(root / sub)     # root / "../../../Scripts" 直接跳出
        sys.path.insert(0, p)   # 无校验直接插入
```

**风险**：当前 4 个 adapter 调用全是硬编码（`inject_vendor_path("caura-memclaw", "core-api/src", "common")`），短期不可利用。但若后续引入从 config 读取 subpath 或调试接口间接传参 → `inject_vendor_path("caura-memclaw", "../../../Scripts")` 会跳出 `vendor/top5`，把 Scratch 目录外的同名包引入 import 劫持链（sys.path[0]）。

**修复**（`_common.py:L51-L112`）：3 层防御 + 失败语义优雅降级
1. **name 边界**：`(_VENDOR_TOP5 / name).resolve().relative_to(_VENDOR_TOP5.resolve())`，越界 → 整体拒绝注入，sys.path 零新增，**不记入** `_INJECTED_VENDORS`（允许下一次重试）
2. **subpath 边界**：每个子路径独立 `resolve().relative_to(_VENDOR_TOP5.resolve())`，越界 → **只跳过敏感那条**，打 WARNING 后继续处理其他子路径（不连累合法子路径与根目录）
3. **根目录存在性**：`root.is_dir()` 检查 vendor 源目录真实存在；不存在 → 跳过根目录注入；若**连子路径也全失败**（added 为空）→ 同样不记入注入记忆，允许后续再重试
4. **IO 错误兜底**：`resolve()` / `is_dir()` 抛 OSError 时 WARNING 不抛异常，注入流程不中断

## 5. 验证完整性声明

1. **所有 HIGH/MEDIUM 风险条目均有对应修复 + 对应 unittest case**，非纯文档性 "TODO 应付"。
2. **跨源查重 HIGH-2 不阻断**：三条写入路径发现冲突只打 WARNING，不拒绝登记。这是**故意设计**而非缺陷，避免 mcporter 新增配置被老 adapter 锁死。用户端通过 `conflict_sources` 字段可以一眼识别，无需看日志。
3. **inject_vendor_path MEDIUM-3 边界校验的 resolve()**：若路径不存在，`Path.resolve()` 在某些系统上会抛 FileNotFoundError → 统一收在 `(OSError, ValueError)` 下按 "跳过敏感路径" 处理。当文件不存在时越界判定偏保守（按越界处理直接跳过），安全侧不牺牲。
4. **测试隔离**：每类 setUp 必调 `mcp_registry.clear_registry()` + `reset_for_tests()`，`_INJECTED_VENDORS` / `_ADAPTER_CAPABILITY_NAMES` / `MANIFEST_CACHE` / `MCP_REGISTRY` 四张表全部清空，跨用例残留 = 0。
